## Purpose
SpecFlow converts a locked `openspec.yaml` into a parallel-ready build plan. It decomposes every functional and non-functional requirement into bounded generation clusters — each cluster is a self-contained unit of code that one AI Builder can generate independently. The output is the primary input to Conductor for task dispatch and to TraceGraph for traceability verification.

---

## Trigger
Invoke after `context.yaml` (ContextFabric) and `policy-catalogue.yaml` (PolicyCatalog) are available.

**Activation phrase:** `Run SpecFlow` or `Decompose sprint spec`

## User Inputs Required

SpecFlow will ask the following if not derivable from the spec:

1. **Iteration mode:** "Is this a new sprint build or iterating on prior sprint artifacts? (new / iterate)"
2. **Builder count:** "How many AI Builders are available for parallel generation? (default: 2)"
3. **Cluster granularity:** "What is the preferred cluster size? (small: 1–3 files / medium: 4–8 files / large: 8+ files) — default: medium"
4. **Ambiguous NFR:** For any non-functional requirement without measurable acceptance criteria, SpecFlow will ask: "Requirement [ID]: '[text]' has no measurable acceptance criterion. Provide a threshold or type SKIP to defer."

## Processing Instructions

### Phase 1 — Requirement Inventory
1. Parse all requirements from `artifacts/openspec.yaml` with their IDs.
2. Cross-reference against `specs/spec.md` and `specs/tasks.md` to confirm scope alignment.
3. Classify each requirement:
   - **Functional (FR):** System behaviour — maps to code modules
   - **Non-Functional (NFR):** Quality attributes — maps to cross-cutting concerns
   - **Integration (IR):** External system interfaces — maps to API/connector modules
   - **Data (DR):** Schema and persistence requirements — maps to database modules

### Phase 2 — Cluster Decomposition
For each requirement group:
1. Identify logical module boundaries (feature, service, UI component, data model, API endpoint)
2. Group requirements into bounded clusters ensuring:
   - No cluster has external dependencies that are not satisfied within the same or a prior cluster
   - Each cluster can be generated by one AI Builder in under half a day
   - Each cluster has a single, clear output artifact (file or set of related files)
3. Assign a cluster ID: `CLU-[NNN]`
4. Map each cluster to its required input context: which spec sections, schema definitions, API contracts

### Phase 3 — Dependency Graph
1. Identify which clusters must complete before others can start
2. Produce a directed dependency graph: `CLU-001 → CLU-003` means CLU-003 cannot start until CLU-001 is complete
3. Identify the critical path — the longest dependency chain

### Phase 4 — Parallel Work Plan
1. Group clusters into parallel execution waves based on the dependency graph
2. Wave 0: no dependencies — can start immediately
3. Wave N: all clusters whose dependencies are satisfied by Wave N-1
4. Assign clusters to builders to balance load across waves

### Phase 5 — Provenance Injection
For every generated source file, inject the following header comment:
```
// SpecPod Sprint: [Sprint ID]
// Requirement: [REQ-ID]
// Cluster: [CLU-ID]
// Generated: [Date]
// human_reviewed: false
```

### Phase 6 — Manifest Update
Append all new artifacts to `artifacts/ai-manifest.json` with spec traceability IDs.

## Output Files

### `artifacts/task-breakdown.yaml`
```yaml
sprint_id: SPRINT-XXX
generated: YYYY-MM-DD
clusters:
  - id: CLU-001
    name: "User Authentication Module"
    requirements: [REQ-001, REQ-002, NFR-001]
    type: functional
    output_files:
      - src/auth/login.ts
      - src/auth/session.ts
    depends_on: []
    wave: 0
    assigned_builder: Builder-1
    estimated_hours: 3
    policy_rails: [POL-GDPR-001, POL-AUTH-002]
    status: READY
  - id: CLU-002
    name: "User Profile API"
    requirements: [REQ-003, REQ-004]
    type: integration
    output_files:
      - src/api/profile.ts
    depends_on: [CLU-001]
    wave: 1
    assigned_builder: Builder-2
    estimated_hours: 2
    policy_rails: [POL-PII-001]
    status: BLOCKED
```

---

## Limitations
- Output quality is bounded by spec completeness. Vague NFRs produce vague code skeletons — POD Lead must review all `human_reviewed: false` artifacts before Gate 1 closes.
- If `context.yaml` is absent, SpecFlow will flag capability assumptions as unverified and reduce confidence scores accordingly.
- Does not generate code directly — produces the plan and provenance-tagged skeletons. AI Builders execute generation per cluster.
