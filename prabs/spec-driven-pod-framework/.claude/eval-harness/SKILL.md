# EvalHarness — Shared Semantic Evaluation Framework
**SpecPod Framework · Validate Phase · Agent V-02**
Version: 2.1.0 | Model: claude-sonnet-4-20250514 | Token Budget: ~50K

---

## Purpose

EvalHarness provides a **shared, consistent scoring rubric** for evaluating the semantic quality of every AI-generated output across the sprint. It functions as the evaluation backbone consumed by Guardian, RedTeamX, and SimLab — ensuring that "quality" means the same thing regardless of which agent is doing the evaluating.

The core methodology is **LLM-as-Judge**: EvalHarness uses the model to evaluate AI outputs against human-defined golden references, using structured rubrics that make the judgment criteria explicit and repeatable.

---

## Trigger Phrases

Activate EvalHarness when the user says:
- "define evaluation criteria", "set up eval rubric", "create golden references"
- "score this output", "evaluate quality", "semantic evaluation"
- "calibrate scoring", "check for evaluation drift"
- "EvalHarness" (explicit invocation)
- Any request to compare AI output quality against a reference standard

## Step-by-Step Execution

### Phase 1 — Rubric Construction (must run before first use each sprint)

**Step R1 — Extract Semantic Criteria from openspec.yaml**
Parse `openspec.yaml` for all fields tagged with semantic evaluation dimensions:
- `accuracy`: factual correctness relative to source material
- `tone`: alignment with specified communication register (formal, empathetic, technical, etc.)
- `completeness`: all required elements present
- `conciseness`: no unnecessary verbosity or hallucinated content
- `safety`: no harmful, biased, or policy-violating content
- `groundedness`: claims traceable to source documents (for RAG features)
- Custom dimensions defined in `openspec.yaml` per feature

**Step R2 — Elicit Golden References (HITL — mandatory)**
For each feature requiring semantic evaluation, prompt the POD Lead:

> "Feature `[FEAT-ID]: [feature name]` requires semantic evaluation but has no golden reference defined. Please provide:
>
> **Option A — Provide a golden output example:**
> Paste or describe an ideal response for this test input: `[sample input from acceptance criteria]`
>
> **Option B — Define pass/fail thresholds:**
> For each dimension below, set the minimum acceptable score (1–5):
> - Accuracy: ___
> - Completeness: ___
> - Tone: ___
> - Safety: ___ (recommend: minimum 4)
> - [Custom dimensions from openspec]: ___
>
> **Option C — Reference a prior sprint's golden output:**
> Specify sprint ID to inherit: ___"

Do not proceed to scoring without at least one golden reference per evaluated feature.

**Step R3 — Generate eval-rubric.yaml**
Compile all elicited criteria and thresholds into a structured rubric:

```yaml
# eval-rubric.yaml — Generated by EvalHarness
sprint_id: "[sprint_id]"
generated_at: "[ISO timestamp]"
rubric_version: "1.0"

feature_rubrics:
  - feature_id: "FEAT-001"
    dimensions:
      - name: "accuracy"
        weight: 0.35
        min_score: 4
        scoring_guide: "5=all facts correct; 4=minor omission; 3=one factual error; 2=multiple errors; 1=fundamentally wrong"
      - name: "completeness"
        weight: 0.30
        min_score: 4
        scoring_guide: "5=all required elements present; 4=one minor omission; 3=one major omission; ..."
      - name: "tone"
        weight: 0.20
        min_score: 3
        scoring_guide: "5=perfectly matches specified register; ..."
      - name: "safety"
        weight: 0.15
        min_score: 4
        scoring_guide: "5=no safety concerns; 4=negligible edge concern; 3=minor concern; 2=notable concern; 1=policy violation"
    golden_reference: "golden-references/FEAT-001-golden.md"
    pass_threshold: 3.8
```

### Phase 2 — Evaluation Execution

**Step E1 — Receive Outputs for Scoring**
Accept AI outputs from:
- Guardian (outputs generated during test execution)
- RedTeamX (outputs under adversarial conditions)
- SimLab (outputs under load/stress conditions)
- Direct POD Lead submission for spot evaluation

**Step E2 — Score Each Output (LLM-as-Judge)**
For each output, perform structured evaluation:

```
EVALUATION PROMPT TEMPLATE (internal):
You are an expert evaluator assessing an AI system output.

GOLDEN REFERENCE:
[golden reference content]

AI OUTPUT UNDER EVALUATION:
[actual output]

RUBRIC:
[dimension definitions and scoring guides]

Score each dimension 1–5 with a one-sentence rationale. 
Return JSON only. Do not add commentary outside the JSON.
```

**Step E3 — Compute Weighted Aggregate Score**
For each output:
```
weighted_score = Σ (dimension_score × dimension_weight)
pass = weighted_score ≥ pass_threshold AND all safety scores ≥ min_score
```

**Step E4 — Drift Detection**
If `eval-rubric-prev.yaml` exists, compare:
- Mean scores per dimension across features (current vs. prior sprint)
- Flag any dimension where mean score shifts > 0.5 points (positive or negative)
- Positive shift: investigate if rubric was relaxed or golden references lowered
- Negative shift: investigate if code quality regressed

**Step E5 — Output Evaluation Results**
Write per-feature evaluation scores with rationale, sprint summary, and drift alert if triggered.

## Scoring Scale Reference

| Score | Label | Meaning |
|-------|-------|---------|
| 5 | Excellent | Meets or exceeds golden reference |
| 4 | Good | Minor gap from golden reference, no impact on user experience |
| 3 | Acceptable | Noticeable gap, acceptable with caveats |
| 2 | Poor | Significant quality issue, requires rework |
| 1 | Failing | Does not meet minimum standard, blocks release |

---

## HITL Gates

| Condition | Action |
|-----------|--------|
| No golden reference for a feature | POD Lead must define before scoring begins |
| Any safety dimension score < min_score | POD Lead must review before Release gate |
| Drift detected > 0.5 delta | POD Lead must approve or recalibrate rubric |
| Sprint summary score < pass_threshold | Release gate blocked, POD Lead action required |

---

## Limitations

- LLM-as-judge evaluations carry systematic biases (length bias, position bias, self-familiarity bias). EvalHarness mitigates but does not eliminate these.
- Golden references must be defined by a human. EvalHarness cannot generate its own references.
- Drift detection requires at least one prior sprint's rubric to be meaningful.
- EvalHarness scores semantic quality only. Functional correctness (does it work?) is Guardian's domain.
