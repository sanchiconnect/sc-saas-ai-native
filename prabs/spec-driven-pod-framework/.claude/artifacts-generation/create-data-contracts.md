**name:** create-data-contracts
**description:** Auto-generates `data-contracts/[entity_name].yaml` files (one per database entity) by reading the database schema, API spec, and domain knowledge from existing specs. Uses the TrustFabric schema definition as the contract format. Fields that cannot be confidently classified are flagged in a post-generation summary.

---

# SKILL: Create Data Contracts

## Purpose
Generate a `data-contracts/` folder with one YAML contract file per database entity so that TrustFabric can validate PII handling, access rules, and data classification during Phase 3. Runs fully automatically from existing specs — unresolvable classifications are flagged in a post-generation summary, not asked interactively.

---

## Inputs

**Required:**
- `specs/database.md` — tables/collections, fields, data types, relationships, retention, compliance

**Supporting:**
- `specs/knowledge.md` — domain entities, business rules, roles, compliance considerations, sensitive data signals
- `specs/api.md` — which fields appear in API responses and under what conditions

**Schema reference:**
- `.claude/trust-fabric/references/data-contract-schema.md` — contract YAML schema definition
- `.claude/trust-fabric/sample_input/sample-data-contract.yaml` — format example

---

## Execution

### Phase 1 — Read Specs

Read `specs/database.md` as the primary source. Read `specs/knowledge.md` for role definitions and compliance signals. Read `specs/api.md` for response field exposure rules.

Read `.claude/trust-fabric/references/data-contract-schema.md` to load the contract schema.

### Phase 2 — Entity Inventory

From `specs/database.md`, extract every table or collection defined.

For each entity record:
- Entity name (exact table/collection name)
- All fields with their data types
- Any retention period or compliance annotation mentioned
- Owning team or role if mentioned

### Phase 3 — PII Classification

For each field in each entity, determine PII class using the following inference rules:

| Signal | Inferred PII Class |
|--------|-------------------|
| name, first_name, last_name, full_name | `PII:IDENTITY` |
| email, email_address | `PII:CONTACT` |
| phone, mobile, telephone | `PII:CONTACT` |
| address, street, postcode, zip | `PII:CONTACT` |
| date_of_birth, dob, age | `PII:IDENTITY` |
| password, password_hash, secret, token | `PII:IDENTITY` |
| ssn, national_id, tax_id, passport | `PII:IDENTITY` |
| bank_account, sort_code, iban, account_number | `PII:FINANCIAL` |
| salary, income, wage | `PII:FINANCIAL` |
| ip_address, device_id, session_id | `PII:TECHNICAL` |
| health, diagnosis, medical, prescription | `PII:SENSITIVE` |
| id, uuid, created_at, updated_at, deleted_at, status, type, version | `NON-PII` |
| amount, total, quantity, count (non-personal financial aggregates) | `NON-PII` |
| reference numbers, codes, flags, booleans not tied to a person | `NON-PII` |

If a field name matches none of these signals and cannot be classified from context in `specs/knowledge.md` or `specs/api.md`:
- Assign `PII:UNCLASSIFIED`
- Add to the post-generation flags list

### Phase 4 — Access Rules

For each entity, derive access rules from:
- Role definitions in `specs/knowledge.md`
- API endpoint access patterns in `specs/api.md`
- Any RBAC or permission constraints in the specs

If roles cannot be determined, use a conservative default:
```yaml
access_rules:
  - role: system_service
    operations: [read, write, delete]
    conditions: "automated processes only"
  - role: admin
    operations: [read, write]
    conditions: null
```
Mark defaulted rules as `[INFERRED]` in the post-generation summary.

### Phase 5 — Masking and Logging Rules

Apply the following defaults per PII class:

| PII Class | encryption_required | logging_permitted | masking_rule |
|-----------|--------------------|--------------------|--------------|
| `NON-PII` | false | true | null |
| `PII:CONTACT` | false | false | "Mask in non-admin responses" |
| `PII:IDENTITY` | true | false | "Return [REDACTED] for non-admin roles" |
| `PII:FINANCIAL` | true | false | "NEVER return in API response without explicit authorisation" |
| `PII:TECHNICAL` | false | false | "Omit from external-facing logs" |
| `PII:SENSITIVE` | true | false | "NEVER return without explicit consent context" |
| `PII:UNCLASSIFIED` | true | false | "REVIEW REQUIRED — treat as PII until classified" |

Override defaults with any explicit spec guidance where found.

### Phase 6 — Generate Contract Files

For each entity, generate `data-contracts/[entity_name].yaml` using the schema from `.claude/trust-fabric/references/data-contract-schema.md`:

```yaml
# data-contracts/[entity_name].yaml
# Generated by: create-data-contracts skill
# Source artifacts: specs/database.md, specs/knowledge.md, specs/api.md
# Generated: [date]
# REVIEW REQUIRED for any field marked PII:UNCLASSIFIED

entity: [entity_name]
version: "1.0.0"
owner: [owning team/role if determinable, else "REVIEW REQUIRED"]
last_reviewed: [generation date]
retention_period: [from spec if available, else "REVIEW REQUIRED"]

fields:
  - name: [field_name]
    pii_class: [classified value]
    description: "[field purpose from spec or inferred]"
    encryption_required: [boolean]
    allowed_roles: [list from access rules]
    masking_rule: [masking rule or null]
    logging_permitted: [boolean]
    purpose_limitation: "[derived from spec context]"

access_rules:
  - role: [role]
    operations: [list]
    conditions: [string or null]
```

Create the `data-contracts/` folder if it does not exist.
Write one file per entity.

---

## Output

- **Folder:** `data-contracts/`
- **Files:** `data-contracts/[entity_name].yaml` — one per entity

---

## Post-Generation Summary

After writing all files, report inline:

- Total entities processed
- Total files written (list each file name)
- Total fields classified
- **Fields requiring POD Lead review** — list every `PII:UNCLASSIFIED` field with entity name, field name, and reason classification could not be inferred
- **Access rules defaulted** — list entities where roles could not be determined from specs
- **Retention periods missing** — list entities where retention period was not found in specs
- Any other assumptions made during generation marked `[INFERRED — validate]`

TrustFabric will flag `PII:UNCLASSIFIED` fields as blockers. The POD Lead must update the relevant contract file and re-run TrustFabric to clear them.
