**name:** program-charter

**description:** Initialize, structure, and generate a complete Program Charter for any software development program. Activate whenever the user says "initialize program", "start a new program", "create a program charter", "set up a program", or begins describing a new software initiative they want to structure formally. Also triggers when a user uploads or references an existing charter and asks to adapt, improve, or re-generate it. Always use this skill before creating any sub-skills, feature briefs, or sprint plans — this is the mandatory first step in the program lifecycle. Produces a fully-structured program.md in specs/ and scaffolds the standard project folder layout.


# Program Charter Skill

## Purpose

Guide the user through a structured elicitation session to capture all dimensions of a software program, then generate a canonical `specs/program.md` and scaffold the standard project folder layout. This is the **entry point** for all program work — no feature briefs, sprint plans, or architecture decisions should precede it.

---

## Activation

Trigger on any of the following:
- `initialize program` / `init program`
- `start a new program` / `create a program`
- `create a program charter` / `write a program charter`
- User describes a software initiative and asks for structure
- User uploads an existing charter and asks to adapt it

---

## Elicitation Protocol

Run the elicitation as a **focused interview**, not a form dump. Ask questions in logical groupings. Wait for answers before proceeding to the next group. Infer where you can and confirm inferences rather than asking redundant questions.

### Group 1 — Foundation (ask first)
1. **Program name** — What is this program called?
2. **Program Lead** — Who owns this program?
3. **Problem Statement** — What problem does this solve? What is the current pain?
4. **Goal / Outcome** — What does success look like in plain language?
5. **Business Impact** — Revenue, cost, efficiency, NPS, or strategic value?

### Group 2 — Scope & Users
6. **Target Users** — Who uses this? Segment by role, region, device, or behavior.
7. **In Scope** — What is explicitly included?
8. **Out of Scope** — What is explicitly excluded (avoid scope creep)?
9. **Success Metrics (KPIs)** — What measurable targets define success? (baseline → target pairs preferred)

### Group 3 — Architecture & Systems
10. **System Domains** — What major system/service domains are involved?
11. **Key Architectural Decisions** — Any known technical choices (API style, caching, auth, compliance)?
12. **Non-Functional Requirements (NFRs)** — Performance, availability, security, scalability, accessibility targets?
13. **Pod / Team Structure** — How many engineering pods? Size and focus of each?

### Group 4 — Design & UX
14. **User Journey** — What are the key steps a user takes end-to-end?
15. **Design Highlights** — Any known UX patterns, interactions, or constraints?
16. **Design System** — Is there an existing design system or component library?

### Group 5 — Delivery & Risk
17. **Timeline** — Quarters or phases with rough goals per phase?
18. **Key Milestones** — Specific dates or gates (sign-off, beta, launch)?
19. **Risk Register** — Known risks with probability, impact, and mitigation?
20. **Stakeholders** — Who are the key stakeholders and their roles?

## Folder Scaffolding

After generating `specs/program.md`, create the following structure in the current working directory:

```
<program-root>/
├── specs/
│   ├── program.md       ← generated by this skill (authoritative charter)
│   ├── knowledge.md     ← stub — populated by spec-knowledge skill
│   ├── design.md        ← stub — populated by spec-design skill
│   ├── ui-ux.md         ← stub — populated by spec-uiux skill
│   ├── database.md      ← stub — populated by spec-database skill
│   └── api.md           ← stub — populated by spec-api skill
├── src/                 ← application source code
├── tests/               ← test suites
├── CLAUDE.md            ← AI collaboration instructions (see template below)
└── .claude/
    └── program-charter/
        └── SKILL.md     ← this skill (already exists if installed)
```

### Spec Stub Format

Create each stub file with a pending notice so pods know it must be completed before use:

```markdown
# {Spec Title}
**Program:** {Program Name}
**Status:** ⏳ PENDING — run `/{skill-name}` to initialize this specification.

This file is a placeholder created by the `program-charter` skill.
It must be populated before any pod begins work that depends on it.
```

Stub files and their initializing skill:
| File | Skill to initialize |
|------|-------------------|
| `specs/knowledge.md` | `spec-knowledge` |
| `specs/design.md` | `spec-design` |
| `specs/ui-ux.md` | `spec-uiux` |
| `specs/database.md` | `spec-database` |
| `specs/api.md` | `spec-api` |

### CLAUDE.md Template

```markdown
# CLAUDE.md — AI Collaboration Guide

## Program
See `specs/program.md` for the authoritative program definition.
All AI-assisted work in this repo must be consistent with that spec.

## Specification Files
All specs live in `specs/`. Read the relevant spec before working in its domain:
- `specs/program.md`   — Program charter, goals, stakeholders, timeline
- `specs/knowledge.md` — Domain entities, business rules, state machines, glossary
- `specs/design.md`    — Tech stack, frameworks, libraries, infrastructure, coding standards
- `specs/ui-ux.md`     — Design tokens, components, motion, accessibility (shared across features)
- `specs/database.md`  — Schema, tables/collections, indexes, migrations
- `specs/api.md`       — REST endpoints, request/response schemas, auth contract

## Key Conventions
- Source code lives in `src/`
- Tests live in `tests/` and mirror the `src/` structure
- All AI pod sessions must read the relevant spec(s) before generating or modifying code
- Spec files are the single source of truth — code must conform to specs, not the other way around
- If a spec needs updating, run the corresponding spec skill before changing code

## Skills
Skills are in `.claude/<skill-name>/SKILL.md`.
| Skill | Purpose |
|-------|---------|
| `program-charter` | Initialize or update the program charter |
| `spec-knowledge`  | Review/update domain knowledge spec |
| `spec-design`     | Review/update technical design spec |
| `spec-uiux`       | Review/update UI/UX spec |
| `spec-database`   | Review/update database schema spec |
| `spec-api`        | Review/update API endpoint spec |
```

## Execution Steps

1. **Greet and orient** — Briefly explain what you're going to do and why.
2. **Run elicitation groups** — One group at a time. Infer where possible; confirm inferences.
3. **Summarize and confirm** — Before generating, present a structured summary and ask for approval or corrections.
4. **Generate `specs/program.md`** — Use the canonical template in `references/program-md-template.md`.
5. **Create spec stubs** — Create `specs/knowledge.md`, `specs/design.md`, `specs/ui-ux.md`, `specs/database.md`, `specs/api.md` as stubs.
6. **Scaffold folders** — Create `src/`, `tests/`, `CLAUDE.md` and `.claude/` structure.
7. **Present output** — List all files created. Show the recommended spec initialization order: knowledge → design → ui-ux → database → api.
8. **Recommended next step** — Suggest the user run `spec-knowledge` first to populate domain entities and business rules, as other specs depend on it.

## Spec Dependency Order

When guiding the user on next steps, always recommend this initialization order:

```
program.md (this skill)
    └── knowledge.md   (spec-knowledge)  ← domain model; all others depend on it
        ├── design.md  (spec-design)     ← tech stack; database + api depend on it
        ├── ui-ux.md   (spec-uiux)       ← design system; independent, can run in parallel
        ├── database.md (spec-database)  ← schema; requires knowledge + design
        └── api.md     (spec-api)        ← endpoints; requires knowledge + database + design
```
