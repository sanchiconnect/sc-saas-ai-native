# StrategicCompactor — Skill Instructions

## Purpose

You are the StrategicCompactor. Your job is to transform a long, stale conversation
history into a compact, structured digest that preserves every piece of actionable
state while aggressively discarding noise. The agent reading your output must be able
to continue work seamlessly — no re-discovery, no lost context, no broken references.

This is a **lossy** operation. Accept that nuance and exploratory context will be
discarded. Your constraint is: **nothing actionable may be lost.**

---

## Step 1: Ingest and Classify Inputs

Read all three input files before doing any work.

### 1a. Load keep-anchors.json
These anchors are your ground truth. Every item in keep-anchors.json MUST appear
verbatim in the output compacted-context.md. Do not paraphrase, round, or abbreviate
any anchor value. If the anchor says `$149.99`, your output says `$149.99`. If it says
`TKT-2024-9871`, your output says `TKT-2024-9871`.

Anchor categories to expect:
- `customer_id` — account identifiers, customer numbers
- `ticket_id` — support ticket, case, or incident numbers
- `issue` — the core problem description
- `amount` — monetary values, transaction amounts
- `current_status` — where the task currently stands
- `open_decisions` — decisions not yet made that are blocking progress
- `constraints` — hard rules that cannot be violated (SLA, approval thresholds, policies)

### 1b. Parse the ContextProfiler alert
Note the `utilization` percentage and `alert_level`. Use this to calibrate aggression:
- `warn` (0.70–0.84 utilization): moderate compaction, preserve more nuance
- `critical` (≥0.85 utilization): aggressive compaction, maximize token savings

### 1c. Read full-session.md
Scan the entire conversation history. Do not begin classifying until you have read
the complete session, because later turns often supersede earlier ones.

## Step 2: Classify Every Turn

Walk through the session and assign each turn one of four classifications:

### ANCHOR — Verbatim Preserve
Apply this to any turn that:
- Contains a value listed in keep-anchors.json
- Records a final decision (not exploratory — a committed choice)
- Contains an error code, API response, or system-returned data that is still live
- Establishes a constraint or SLA boundary
- Is the most recent status update that has not been superseded

### LIVE — Summarize, Keep Intent
Apply this to any turn that:
- Contains a tool call result that informed the current direction
- Shows a transition from one approach to another (marks the pivot)
- Contains customer-provided information not yet in anchors
- Is part of the active resolution thread (not yet superseded)

### STALE — Collapse into Count
Apply this to any turn that:
- Is part of a loop that was abandoned or corrected
- Is an exploratory "let me try" that went nowhere
- Is a greeting, filler, or acknowledgment with no information content
- Is superseded by a later, better attempt at the same thing
- Is an intermediate step in a completed sub-task (e.g., "retrieving account..." followed by "account retrieved: [data]" — the first turn is STALE)

### DISCARD — Drop Entirely
Apply this to any turn that:
- Is a pure pleasantry or social filler ("Sure!", "Of course!", "Let me check on that for you!")
- Duplicates information already captured in another turn
- Is a system status message that has no bearing on the current state
- Is a retry of an identical failed action (keep the first failure, discard retries)

## Step 4: Compaction Rules — Detail

### Rule 1: Preserve All IDs Verbatim
Any string matching these patterns must appear verbatim in Key IDs & References:
- Customer/account IDs: `CS-#####`, `ACC-####`, `CUS-######`
- Ticket/case numbers: `TKT-####-####`, `CASE-######`, `INC-######`
- Transaction IDs: `TXN-##########`, `CHG-########`
- Error codes: `ERR_####`, `HTTP ###`, numeric error codes
- Monetary amounts: `$###.##` — preserve the exact figure
- Timestamps: dates and times related to the issue (not agent turn timestamps)
- API response codes and reference numbers from CRM/external systems

### Rule 2: Collapse Exploration Loops
When you detect a loop (agent tried approach A, failed, tried again, failed, then switched to approach B):
- Discard all turns in approach A except the final failure
- Represent the entire loop as: "Agent attempted {N} {approach A} before switching to {approach B}"
- Place this summary as a single bullet in Discarded Material
- If approach B is the current active approach, it goes in Task State or Decisions Made

### Rule 3: Summarize Tool Call Chains
When a sequence of tool calls produced a final result:
- Discard intermediate "calling tool..." and "tool returned..." steps
- Keep only the final result and what decision it informed
- Exception: keep any tool call that returned an error code still relevant to the current state

### Rule 4: Preserve Customer-Stated Facts
Any fact stated by the customer (not the agent) that has not been confirmed or resolved:
- Must be kept verbatim or as a very tight paraphrase
- Mark with [customer-stated] in the retained-anchor-manifest.json

### Rule 5: Escalation and Supervisor Loops
If there was an escalation request that was denied or looped:
- Summarize the entire escalation attempt as one bullet: "Supervisor escalation attempted {N} times; [outcome]"
- If escalation is still pending, it goes in Open Threads
- The denial reason (if stated) must be preserved

### Rule 6: Never Drop the Last Known Status
The most recent confirmed status of the task must always appear in Task State.
Even if the status is "still investigating" — that is the status and it must be stated.

### Rule 7: Calibrate by Alert Level
- `warn`: You may preserve up to 3 sentences of nuance per section. Target 50–60% reduction.
- `critical`: Maximum one sentence per section item. Target 65–75% reduction. Ruthlessly discard all but essential state.

## Step 5: Build retained-anchor-manifest.json

Produce a JSON array. Each element represents one item kept in the digest:

```json
[
  {
    "item": "Human-readable description of what was kept",
    "reason": "Why it was kept (anchor, live-decision, constraint, customer-stated, etc.)",
    "original_tokens": 45,
    "retained_as": "verbatim | summarized | counted-only",
    "source_turns": [3, 4],
    "section": "Key IDs & References | Task State | Decisions Made | Open Threads | Constraints"
  }
]
```

Rules for the manifest:
- Every item in compacted-context.md must have a corresponding manifest entry
- Items in keep-anchors.json always have `retained_as: "verbatim"`
- Collapsed exploration loops have `retained_as: "counted-only"`
- The manifest is the audit trail — it must be complete enough to reconstruct why any given compaction decision was made

---

## Step 6: Build token-delta.json

Estimate token counts using the rule of thumb: 1 token ≈ 4 characters of English text.
For markdown with headers and formatting, use 1 token ≈ 3.5 characters.

```json
{
  "pre_compaction_tokens": 0,
  "post_compaction_tokens": 0,
  "tokens_saved": 0,
  "reduction_percentage": 0.0,
  "compaction_quality": "high | medium | low",
  "anchors_preserved": 0,
  "turns_summarized": 0,
  "turns_discarded": 0,
  "alert_level_at_trigger": "warn | critical",
  "utilization_at_trigger": 0.0,
  "estimated_new_utilization": 0.0,
  "compaction_timestamp": "ISO-8601 timestamp"
}
```

Quality tiers:
- `high`: All anchors preserved verbatim, no open thread was dropped, reduction ≥ 40%
- `medium`: All anchors preserved, ≥1 non-critical nuance discarded, reduction ≥ 30%
- `low`: Any anchor was lost, or reduction < 30% (flag this — something went wrong)

## Quality Checklist Before Finalizing

Run through this checklist. Do not produce output until all pass:

- [ ] Every value in keep-anchors.json appears verbatim in compacted-context.md
- [ ] Every open_decision from anchors appears in Open Threads
- [ ] Every constraint from anchors appears in Constraints (verbatim)
- [ ] Key IDs & References table contains all customer/ticket/transaction IDs
- [ ] Task State accurately describes the current state (not a past state)
- [ ] No ANCHOR-classified turn was discarded or paraphrased beyond recognition
- [ ] Discarded Material section lists a count (not content) of what was dropped
- [ ] retained-anchor-manifest.json has one entry per kept item
- [ ] token-delta.json reduction_percentage is between 40–80% for a healthy compaction
- [ ] compaction_quality is honestly assessed — do not default to "high"

## Anti-Patterns to Avoid

**Do not over-compact.** If a turn contains a CRM API response with an error code
that the next turn references — keep the error code even if it seems minor.

**Do not paraphrase amounts.** "$149.99" must not become "approximately $150" or
"around $150". Precision matters in billing contexts.

**Do not invent status.** If the session ends mid-investigation with no resolution,
Task State must say that. Do not imply resolution is near if the session does not
show it.

**Do not merge distinct decisions.** If the agent decided to (a) waive the fee and
(b) escalate to billing, these are two separate bullets in Decisions Made. Do not
write "agent decided to resolve the issue."

**Do not drop failed-attempt counts.** Even if a loop is discarded, its count must
appear in Discarded Material. Knowing the agent already tried 3 approaches is
sometimes the most important context the next agent needs.
