## Problem

CFA ("Custom Programs") has **no reapply flow** for a rejected startup applicant, while legacy Program Management has a full one. This is a frontend-only gap — the backend already implements reapply for CFA.

**Backend (works today):** `ApplicationProgramService.applyForProgram()`
(`sc-saas-backend/src/modules/application-management/application-program.service.ts`) already handles reapply as its natural re-entry point: when no submission-round row exists yet for the given `submissionId`, it looks up the startup's most recent prior round (`getLatestSubmissionRoundForStartup()`). If that prior round `isRejected`:
- Blocks outright (`ForbiddenException(REAPPLICATION_NOT_ALLOWED)`) if `program.allowReapplication` is `false`.
- Otherwise computes a cooldown-activation date via `getReapplyActivationDate(priorRound.rejectedOn, program.reapplicationTime, program.reapplicationDurationType)` (`day`/`month`/`year`/`immediate`), using the prior round's own `rejectedOn` as the sole cooldown baseline.
- Blocks with a "You can reapply in N day(s)…" message if the cooldown hasn't elapsed.
- **Revised 2026-08-17 (second revision — reset-in-place):** if eligible, **reuses the existing `ApplicationProgramSubmissionRoundsEntity` row** rather than creating a new one — moves it onto the new `submissionId`, resets `isRejected`/`rejectedOn`/`rejectionMessage`/`applicationStatus`/`submissionStatus`, and appends a `{ action: 're-applied', ... }` entry to its `completedRounds` JSON column. This now mirrors Program Management's `updateStartupProgramStatus()` exactly (explicit product decision, per direct user instruction: "use existing row/application for re-apply every time, only update the history json of that record"), superseding the original "always creates a new row" design this spec started with. A first-time application (no prior round at all) still creates a brand-new row.
- **Revised 2026-08-17 (third revision — `applicationNumber` stability):** the reset-in-place logic above initially still recomputed `applicationNumber` from the new `submissionId` on every reapply. Confirmed via a real end-to-end test as the direct cause of a "created a new application again and again" report — the admin kanban's total-submissions count correctly stayed constant (proving no new row was actually inserted), but the visible `APPxxxxx` label changed on every reapply, which read as a brand-new application regardless of what the DB actually did. Fixed: `applicationNumber` is no longer touched on the reuse path — it's set once, at first-time application, and stays that row's stable identity for its entire history, including every subsequent reapply.

**Revised 2026-08-17 (first revision) — `startup_reapplication_history` removed from CFA entirely.** An earlier pass of this implementation (and pre-existing SAN-253 code predating this spec) had CFA read/write `startup_reapplication_history` for cooldown-baseline lookup and attempt accept/reject status tracking, mirroring Program Management. That table is keyed only by `(startupId, programId)` with no column distinguishing the `programs` table (legacy) from `application_programs` (CFA) — since each table auto-increments its own `id` independently, a legacy program and a CFA program sharing a numeric id for the same startup could silently collide (wrong cooldown baseline, shared attempt counter). Per explicit product decision, CFA no longer touches this table at all — `applyForProgram()`'s reapply gate and `getReapplyEligibility()` (below) both use only the round's own `rejectedOn`/`completedRounds`. `startup_reapplication_history` remains exactly as-is for Program Management — untouched by this spec.

**Trade-off of the reset-in-place revision, explicit and deliberate (verified via a dedicated check of `sc-saas-admin`'s Custom Programs kanban/list query before implementing):** CFA's jury/ratings/notes/documents are all keyed by `submissionId`, not by the round row's own id. Moving the round row onto a new `submissionId` on reapply means the OLD (rejected) submission's evaluation data stays in the DB but becomes unreachable from any admin screen — `application_program_submission_rounds_view` (backing both the kanban and table views, `sc-saas-admin/includes/table_views_functions.php` + `includes/application_program_management_funcs.php`) is a flat, ungrouped per-row projection with no dedup/history mechanism, so the prior rejected attempt's card disappears from the admin's Custom Programs kanban/list the moment a startup reapplies. **This matches Program Management's own reference behavior exactly** (`program_startup_rounds` is structurally one row per startup+program, always reset in place — its admin kanban has never shown separate cards per past rejected attempt either), so this is CFA converging onto the same model the reference already uses, not a new class of data-loss risk — confirmed and accepted explicitly by the user before implementation, not assumed.

**Frontend (does not exist):**
- Zero matches for `reapply`/`isRejected`-gating anywhere in `sc-saas-frontend/src/app/modules/call-for-applications/` or `program-public-apply.component.ts` — no button, no gating, no messaging.
- Compare to Program Management's real reapply UI: `program-details-top-bar.component.ts`'s `checkReapplyEligibility()`/`getReapplyDate()` gate an "Enable Application" button (`onEnableApplication()` → `profileService.onEnalbleApplication()` → `POST programs-management/update-startup-program-status`). That endpoint **resets the existing round in place** — architecturally different from CFA's always-a-fresh-submission model, so this logic cannot be reused verbatim; CFA needs to route the user into a **new** form submission instead.
- The CFA "View Application" link is actively **mis-routed** today: `call-for-applications-card.component.ts`'s `ngOnInit()` sets `urlsMap.applied = /programs/applied/${uuid}` for both `ProgramType.CALL_FOR_APPLICATION` and `ProgramType.PROGRAM` alike (`call-for-applications-card.component.ts:73-79`). That route resolves to `ProgramsDetailsPageComponent`, whose `fetchProgram()` calls `publicApi.fetchSingleProgramManagement(id)` → `GET programs-management/:id` (`programs-details-page.component.ts:222-223`) — a **legacy-Program-Management-only** endpoint querying the `programs` table. A real CFA program (table `application_programs`) cannot resolve correctly through it. This is a real bug, not just a missing feature, and needs fixing as part of this work.
- The correct CFA apply page already exists and is reachable at `apply/:code/:slug` → `ProgramPublicApplyComponent`. Its `onFormSubmitted()` already calls the correct CFA endpoint (`publicApi.applyApplicationProgramsManagement()` → `POST application-programs-management/:programId/:submissionId/apply`, `public-api.service.ts:173-174`) — it is the right destination for a CFA reapply, it just has no rejected-state awareness today.
- A rejected applicant returning to this page (with `applicationMeta.email` known) already receives `isRejected`/`rejectedOn`/`rejectionMessage` on the round-detail object via `applicationProgramManagementApplicationDetails()` → `checkApplicationStatus(programUUID, email, true)` (`application-program.service.ts:1065-1106`, via `getProgramRoundDetails()` at `:966-1009`) — but the component only uses this to render a read-only **status/rounds tab view** (`applicationStatusTabs`, `program-public-apply.component.ts:371-397`); there is no branch that offers "start a new application" when eligible.
- `isRejected` was added this session as a flat field on `checkApplicationStatusMultiple()`'s per-program response (`application-program.service.ts:1115-1164`) and now correctly drives a "Rejected" badge on the Programs grid card (`call-for-applications.component.ts`'s `isRejectedProgram()`, card's `isRejected` `@Input()`). That plumbing works; reapply *eligibility* is the next, unbuilt layer — `checkApplicationStatusMultiple()` returns only `{ programUUID, status, isDraft, isRejected }`, with no cooldown/eligibility info and no program object at all, so the grid card cannot show a "Re-apply" affordance without a backend response extension.
- Admin already supports configuring this per program — "Allow Re-application" toggle + Duration Type (`Immediate`/day/month/year) on `application_management/program/{id}/edit/{slug}` in `sc-saas-admin` (confirmed via screenshot this session, and via SAN-343/SAN-344's shipped `Immediate` option). Operators can already turn this on; the startup-facing flow to act on it for CFA is what's missing.

## Acceptance criteria

- [x] A rejected CFA applicant whose program has `allowReapplication = true` and whose cooldown has elapsed can see, without having to guess, that they are eligible to reapply — both on the Programs grid card and on the CFA apply page (`ProgramPublicApplyComponent`) — and can act on it to reach a fresh, blank application form for that program. *(Implemented; the row-duplication trade-off originally noted here was found in production testing and fixed 2026-08-17 — see the acceptance criterion below.)*
- [x] A rejected CFA applicant still inside the cooldown window sees a "you can reapply on `<date>`" style message in place of the card's second button, instead of a dead-end "Rejected" badge with no next step.
- [x] A rejected CFA applicant on a program with `allowReapplication = false` sees messaging consistent with "reapplication is not allowed for this program" (mirrors backend's `ApiErrors.REAPPLICATION_NOT_ALLOWED`) in place of the card's second button, rather than a dead-end.
- [x] `checkApplicationStatusMultiple()`'s response includes enough information for the Programs grid to render the above three states without an extra round-trip per card — computed via the existing `getReapplyActivationDate()` cooldown math (`application-program.service.ts:119-139`), not a new/duplicated implementation.
- [x] The CFA "View Application" link (`call-for-applications-card.component.ts`'s `urlsMap.applied`) no longer routes a `ProgramType.CALL_FOR_APPLICATION` program through the legacy `GET programs-management/:id` endpoint. It resolves to a page that correctly loads CFA data (`application_programs` table) for that program.
- [x] Reapplying creates a genuinely new *form submission* (new `submissionId`, fresh answers) even though the *round row* tracking that submission is now reused in place (see the reset-in-place revision above) — consistent with the backend's reapply model: a new submission, tracked on the startup's one persistent round row. **Revised 2026-08-17 — row-duplication bug found in production, fixed (originally flagged here as an accepted "abandoned draft rows" trade-off; this is now a real fix, not a documented limitation):** the public forms-management submission endpoints (`sc-saas-backend`'s `form-management` module) resolve/upsert a `form_submissions` row purely by `(formId, email)`, with no way to target a specific `submissionId` — the frontend's original workaround (setting `multipleAccepted: true` on every save during a reapply session) inserted a NEW row on every ~20s autosave tick, not just the final submit, confirmed via the admin kanban showing 5 separate cards for one applicant's single reapply attempt. Fixed by adding a `submissionId` field to `PublicFormSubmissionDto` and a matching `FormsRepository.getPublicFormSubmissionById()`: the frontend now sends `multipleAccepted: true` only on the session's first save, captures the id it returns, and sends that id back as `submissionId` on every save after — which the backend resolves deterministically instead of inserting again. Also fixed a compounding bug in the same backend branch: it previously hardcoded `submitted = true` and sent the "form submitted" confirmation email on every autosave (not just a real submit), regardless of `formSubmissionDto.submitted`. Covered by 6 new backend jest tests (`form-management.service.spec.ts`). See `sc-saas-frontend`'s `dynamic-forms`/`programs` module specs and `sc-saas-backend`'s `form-management` module spec for the full writeup.
- [x] **Revised 2026-08-17:** the reapply attempt does NOT round-trip through `startup_reapplication_history` — that table was removed from CFA entirely (see Problem section), not preserved. `applyForProgram()`'s cooldown gate now uses only the round's own `rejectedOn`; this is a genuine, deliberate behavior change to the write-side gate (not purely a read-side addition as originally scoped), made because the table risked cross-type collisions with Program Management and was redundant for CFA's fresh-submission model regardless.
- [x] **Revised 2026-08-17 (second revision):** a reapply now reuses the startup's existing `ApplicationProgramSubmissionRoundsEntity` row (reset in place, `completedRounds` JSON logs the transition) instead of creating a new row per attempt — see the Problem section's reset-in-place revision and its admin-kanban trade-off note.
- [x] Non-startup CFA applicant types (investor/mentor/corporate/program_office/service_provider/individual) are entirely unaffected — reapply eligibility only ever applies to `submittingStartup`-resolved applicants, exactly as `applyForProgram()` already scopes it.
- [x] `Immediate` duration type (SAN-343) is handled correctly wherever the frontend surfaces a cooldown date — i.e., an eligible-immediately applicant never sees a spurious "reapply on `<date>`" message.

## Per-repo plan

### backend

- `src/modules/application-management/application-program.service.ts`:
  - Extend `checkApplicationStatusMultiple()` (`:1115-1164`) to additionally compute, for the `isRejected: true` case, whether reapply is currently allowed and (if not yet) when it becomes eligible. Reuse the existing private `getReapplyActivationDate()` (`:119-139`) against the rejected round's own `rejectedOn` — the same call `applyForProgram()` already makes — rather than adding a second implementation of this cooldown math. Requires resolving the submitting startup for each `programUUID` in the loop (the same `formSubmission.userId` → `user.startupId` chain already used in `applyForProgram()`, `:377-386`) since `checkApplicationStatusMultiple()` currently keys only off `formId`+`email` and doesn't resolve a startup today — confirm at implementation time whether every caller of this endpoint is a startup-context caller, since (like `applyForProgram()`) CFA also serves non-startup stakeholder types for which reapply eligibility doesn't apply. Does NOT use `startup_reapplication_history` — see the Problem section's 2026-08-17 revision for why.
  - Extend the round-detail object returned by `getProgramRoundDetails()` (`:966-1009`, consumed via `checkApplicationStatus(showDetails=true)` at `:1065-1106`, which backs `ProgramPublicApplyComponent`'s `applicationProgramManagementApplicationDetails()`) with the same reapply-eligibility fields, for symmetry with the grid-card contract.
  - Also include `program.allowReapplication` in both responses so the frontend never has to special-case "reapply not allowed at all" vs. "still in cooldown" via a different data source.
  - **Revised 2026-08-17:** `applyForProgram()`'s write-side gate (`:396-489`) DID change — its cooldown baseline now uses only the round's own `rejectedOn` instead of also consulting `startup_reapplication_history` (removed for CFA entirely, see Problem section). The read-side `getReapplyEligibility()` must still never drift from what `applyForProgram()` actually enforces at write time (client-side eligibility display is UX-only, not a security boundary — the real gate stays server-side in `applyForProgram()`) — both now derive the baseline the same way.
  - No DTO change to `CheckApplicationStatusDto` (`dto/check-status.dto.ts`) — only response shape changes on two existing routes, both additive (new fields only).

### frontend

- `call-for-applications-card.component.ts` / `.html`: consume the new reapply-eligibility fields from `checkApplicationStatusMultiple()` to replace the card's existing second button (today: `Applied`/`View Application`/`Apply`) with one of three states when `isRejected` is true: **eligible-now** → a "Re-apply" CTA that navigates into the fresh-application entry point (see below); **in-cooldown** → a disabled button/label showing "You can reapply on `<date>`"; **not-allowed** (`allowReapplication = false`) → a disabled button/label reading "Reapplication not allowed". The "Rejected" badge (`call-for-applications-card.component.html:15-16,118`) stays as-is in all three cases — it is not replaced, only the button beneath/beside it changes.
- Fix the CFA mis-route: `ngOnInit()`'s `urlsMap` block (`:73-79`) currently sends both `ProgramType.CALL_FOR_APPLICATION` and `ProgramType.PROGRAM` to `/programs/applied/${uuid}` (`ProgramsDetailsPageComponent`, legacy-only). Route `ProgramType.CALL_FOR_APPLICATION` to a URL that resolves through `ProgramPublicApplyComponent` (`apply/:code/:slug`) instead, since that component already has the working CFA status/rounds-tab rendering (`:371-397`) this link needs. For a logged-in startup, resolve identity from `profileDetails.email` (the same NgRx `getProfileData` selector already wired into this component's `applicationMeta`-adjacent state) instead of relying on the guest OTP/`localStorage` flow — populate/seed the `application-${uuid}` localStorage entry (or an equivalent in-memory value `applicationMeta` already reads) directly from `profileDetails.email` when a session exists, bypassing OTP entirely for that case. The existing guest/OTP flow is unchanged for logged-out visitors.
- `program-public-apply.component.ts`: when `applicationStatus.isRejected` is true (already available via `applicationProgramManagementApplicationDetails()`, `:328-397`) and the new eligibility fields say reapply is allowed and the cooldown has elapsed, show an explicit intermediate "Start New Application" step — a short summary (e.g. "Your previous application was rejected on `<rejectedOn>`. You're eligible to reapply.", including the prior rejection reason if the program captured one, per `roundDetail.rejectionMessage`/equivalent) with an action button that then reveals a **new, blank** form submission (new `submissionId`) — it must not auto-show the blank form on page load, and must not silently overwrite/pre-fill from the old rejected submission. When still in cooldown or `allowReapplication` is false, show the equivalent disabled-state messaging (mirroring the grid card's copy) in place of the "Start New Application" action, alongside the existing rejected-status/rounds-tab view.
- Handle `Immediate` duration type identically to `day`/`month`/`year` wherever a reapply date is displayed — do not port Program Management's `profile.service.ts`'s `getReapplyDate()` (`:180-200`) as-is, since that copy has no `Immediate` case (SAN-343 explicitly left the Program Management frontend untouched) and because CFA should consume the backend's precomputed eligibility fields rather than re-deriving cooldown math client-side a second/third time.
- No change to `api-endpoint.service.ts` route constants — both extended endpoints already exist and are called today; only their response shape gains fields.

## Contracts & invariants

- **Flags:** none. `allowReapplication`/`reapplicationDurationType`/`reapplicationTime` are per-program columns (`application_programs` table), not tenant flags — consistent with SAN-343's precedent.
- **API:** `POST application-programs-management/check_application_status_multiple` and `POST application-programs-management/:programUUID/check_application_status/:email/details` both gain new, additive response fields (reapply eligibility + `allowReapplication`). No existing field is removed or renamed, no request shape changes.
- **Events:** none.
- **Invariants at risk:**
  - *API contract (#2)* — both changes are additive-only; run `/audit-contract` before `in-review` to confirm no frontend consumer assumes an exact/closed response shape (e.g. strict DTO validation) that an added field would break.
  - *Tenant scoping (#5)* — all data involved (`application_programs`, `application_program_submission_rounds`) is read through the backend's existing one-deployment-per-tenant repositories; no new query pattern or cross-tenant read is introduced.
  - Flag names (#1), tenant-verification contract (#3), auth (#4), and PowerPitch (#6) — not touched.

## Rollout

Backend ships first (additive response fields only — inert until the frontend reads them, so safe to deploy standalone). Frontend ships second, consuming the new fields. No migrations, no flag gating needed — this is a pure read/UX addition on top of an already-live backend write path (`applyForProgram()`'s reapply handling has been live since SAN-253).

## Out of scope

- Any change to Program Management's own reapply flow (`program-details-top-bar.component.ts`, `updateStartupProgramStatus()`) or its use of `startup_reapplication_history` — that table and mechanism remain exactly as-is for Program Management; only CFA's (separate, since-removed) use of that table was in scope here.
- Any admin-side (`sc-saas-admin`) change — the "Allow Re-application"/Duration Type configuration UI already exists and is unaffected; no gap was found there.
- Surfacing attempt-count metadata to the applicant — decided out of scope for v1 (see Design decisions #4); only the prior rejection reason/message is shown, using the round-detail field already returned today. (Moot now that CFA doesn't use `startup_reapplication_history`'s `attemptNo` at all — there is no attempt-count data left to surface even if a future spec wanted it; it would need a new counter derived from CFA's own submission-round rows.)

## Design decisions (resolved 2026-08-17, supersedes the original Open questions)

- **(#1) Messaging/placement:** the card's existing second button (`Applied`/`View Application`/`Apply`) is replaced, not supplemented, by one of the three reapply-state buttons described in the frontend per-repo plan above. The "Rejected" badge is unchanged in all three states — it identifies the outcome; the button communicates the next action (or its absence).
- **(#2) Identity resolution for the fixed "View Application" route:** a logged-in startup resolves identity from `profileDetails.email` (NgRx `getProfileData`), bypassing the guest OTP/localStorage flow entirely. The existing guest/OTP flow is preserved unchanged for logged-out visitors — this is additive, not a replacement of that path.
- **(#3) Reapply entry step:** an explicit "Start New Application" intermediate step is required — landing on the apply page as an eligible, cooldown-elapsed rejected applicant must never auto-show a blank form. The intermediate screen states the prior rejection date (and reason, per #4) and requires an explicit action before the new form appears.
- **(#4) Reapply history surfaced to the applicant:** show the prior rejection reason/message only (the round-detail `rejectionMessage`-equivalent field already returned by `checkApplicationStatus(showDetails=true)`), presented in the "Start New Application" intermediate screen from #3. Do not surface `startup_reapplication_history.attemptNo` or any other raw attempt-count metadata.
