# Startup ID Creation Module + Program/Round Configuration Controls

## Problem

Startup incubators/accelerators using SanchiConnect need a tenant-configurable, composite Startup ID
(e.g. `TR26-GOM-UDPR-000326`) issued to a startup when it is recognised in a program round, plus a
printable/downloadable Digital ID Card carrying that code — today no such mechanism exists (the only
adjacent feature is the unrelated, tenant-self-service `startup_id_cards` module already in
`sc-saas-admin`/`sc-saas-backend`, evidenced below). Separately, program/round creation needs two new
and two overlapping configuration toggles to support reapply-after-rejection cooldowns and
Startup-ID-gated program eligibility. This spec is sourced from Linear **SAN-253**, which bundles a
fully-reviewed BRD (v1.4, "Startup ID Creation Module") with a second, materially less-specified
requirement ("Program & Round Configuration Controls") that the issue itself says needs its own design
pass. This document traces both against real code per `specs/spec-authoring-practices.md` and carries
forward every unresolved decision rather than inventing answers.

**Architecture note (2026-08-08, supersedes the BRD's central premise)**: the BRD's own repeated framing — "almost none of this configuration is exposed to the tenant itself," format/location/card-design decisions "centralised with the platform team," no tenant-side role "at any permission level" able to reach these screens — is **explicitly reversed** in this spec. The Format Builder, Location Master, and Digital ID Card Design Builder are tenant self-service, in `sc-saas-admin`, not platform-operator-only in a separate Admin Portal. See Per-repo plan → admin for the full resolution and what this changes.

## Evidence-tagging convention used throughout this spec

- **Evidenced** — cited to `file:line` in the real codebase.
- `[INFERRED — requires validation]` — a reasonable extrapolation, not directly stated in the source brief or code.
- `[NOT SPECIFIED IN SOURCE]` — a real gap; neither the BRD nor the code says either way.
- `[DESIGN DECISION PENDING]` — a genuinely new decision with no precedent to ground it in.

## Acceptance criteria

**Startup ID module (Part 1)**
- [ ] `startup_recognition_enabled` exists on `tenant_users`, defaults `false`, is backfilled for existing tenants, and is the sole tenant-side gate surfaced to backend/frontend/admin (no separate master control).
- [ ] A tenant with the flag off sees no Startup ID UI anywhere (frontend panel hidden, admin toggles hidden/disabled, backend routes return `403`/feature-guard rejection even via direct API call).
- [ ] Format Builder (**resolved 2026-08-08 — in `sc-saas-admin`, tenant self-service, Developer-only role**, not the platform-operator Admin Portal) lets a tenant's own Developer role add/remove/reorder any of Country Code, State Code, Year of Recognition, District, City, Sub-Division, Spoke, Serial No. with none locked as mandatory, and preview a sample assembled code + affected-count before saving. **Resolved 2026-08-08 — collapses the earlier two-segment "Hub" + "Spoke" design into one segment, "Spoke"**: see Per-repo plan → backend for why Hub was never a real data value.
- [ ] Saving a changed format triggers an async, chunked, audited regenerate-all of every `startups` row already holding a `recognition_id` under the tenant, preserving stored source values and only reassembling the string; a segment removed from the format simply disappears from newly-assembled codes.
- [ ] The assembled code is stored in a column/property named `recognition_id`/`recognitionId`, never `startup_id`/`startupId`.
- [ ] The serial counter is atomic (locking read or `INSERT...ON DUPLICATE KEY UPDATE`+`LAST_INSERT_ID`, not `SELECT MAX()+1`), zero-padded to a minimum of 6 digits, continuous, and increments regardless of whether Serial No. is in the visible format. **Resolved 2026-08-07**: no hard stop at `999,999` — the counter extends to 7+ digits past that point rather than failing generation (supersedes the BRD's fixed-6-digit assumption).
- [ ] A `recognition_id` collision (or a format that omits Serial No.) triggers an auto-appended disambiguating suffix on write rather than a failed insert or a duplicate; the assembled-code column carries a UNIQUE index as the hard backstop.
- [ ] Round entry generates a Startup ID exactly once per startup ever, only when `generate_recognition_id` is true on the triggering round AND the tenant's `startup_recognition_enabled` is true, checked idempotently at the shared backend round-transition layer (not per admin-UI entry point).
- [ ] **Resolved 2026-08-07, relocated 2026-08-08**: a separate, manual "Generate ID" action exists in `sc-saas-admin`'s Startup ID Management module, letting the tenant's own Super Admin/Owner or Developer Admin trigger generation for a specific startup on demand, independent of round-entry. Shares the same idempotency rule as round-entry generation — no-ops or errors clearly if the startup already holds an active Startup ID, never silently regenerates (regeneration is the separate, tenant-wide, format-change-triggered flow only).
- [ ] `freeze_applications` blocks move/reject/mark-tentative on any application already in a frozen round, enforced at the same shared backend layer.
- [ ] Every StartupRecognitionIdModule mutating endpoint re-checks `Feature.STARTUP_RECOGNITION_ENABLED` server-side (does not repeat the documented `startup_id_cards`-style render-time-only gating gap).
- [ ] Location Master (**relocated 2026-08-08 — `sc-saas-admin`, tenant self-service**) supports District/City/Sub-Division registry-search-and-match against `StandardGeographyEntity` with a `manual_entry` fallback; codes are unique per type per tenant; rows are soft-deleted (`active` flag) since `startups` rows may reference them via `district_id`/`subdivision_id`. **Resolved 2026-08-08 — Hub/Spoke removed from Location Master entirely**: it is not a new registry (see Per-repo plan → backend) — the abbreviation lives as a new field on the existing Partner entity/form instead.
- [ ] Digital ID Card Design Builder (**relocated 2026-08-08 — `sc-saas-admin`, tenant self-service, Developer-only**) renders a true CR80 (85.6×54mm) canvas, supports static-asset and data-bound layers, and a Preview-with-Sample-Data mode; saves apply immediately with no regeneration step (presentation-only).
- [ ] All `digital_id_card` screens, now in `sc-saas-admin`, are gated by role tier — **resolved 2026-08-07, supersedes the earlier hardcoded `ai_credits`-style check; relocated 2026-08-08 from the Admin Portal to `sc-saas-admin`'s own role system; simplified 2026-08-08 (final) — the granular Create/View/Edit/Generate ID permission module was dropped per explicit request** before its supporting `spa_admin_roles` columns were ever applied to any tenant DB. Access is now purely role-tier based: the tenant's own **Super Admin/Owner and Developer Admin** roles (confirmed 2026-08-08 — this reverses the BRD's explicit statement that Tenant Developer Admin has *no* access to this configuration "in any form"). Format Builder + Card Design Builder are further narrowed to Developer Admin-only within that pair (see Per-repo plan → admin).
- [ ] `sc-saas-admin`'s existing round-edit screen gains `Generate Startup ID` (disabled + tooltip when the tenant flag is off) and `Freeze Application` toggles.
- [ ] `sc-saas-frontend`'s account page shows a read-only Startup ID + segment breakdown when the flag is on, and is absent when off.

**Program/Round configuration controls (Part 2)** — **resolved 2026-08-07, and Hub/Spoke fully resolved 2026-08-08**: product/dev lead has now answered every open question for this half (see Open questions).

- [ ] Reapply-after-rejection cooldown is scoped **per-program**, enforced on both the frontend (reapply CTA shows remaining wait time, disabled until elapsed) and the backend (rejected at submit-time if the cooldown hasn't elapsed) — not frontend-only.
- [ ] Existing `rejectedOn` is kept and reused as the baseline rejection timestamp for the original application; every subsequent reapply attempt is recorded as its own row in a new `startup_reapplication_history` table (**resolved 2026-08-07**, replacing the earlier numbered-column design — see Per-repo plan → backend).
- [ ] The Restrict-to-Startup-ID-holders message is stored in a **new** dedicated column — not the existing `rejectionMessage` columns — revealed via an inline textbox directly below the toggle at the moment it's switched on, prompting "Please type the rejection message."
- [ ] A logged-out applicant on a Restrict-to-Startup-ID program is redirected to the login page (not shown an inline prompt pre-login).
- [ ] A logged-in applicant with no active Startup ID sees an inline prompt the moment they click **Apply** (not pre-emptively on page load), telling them a Startup ID is required.
- [ ] The Restrict-to-Startup-ID gate is enforced on both the frontend (blocks at the Apply click) and the backend (rejected at submit) — not frontend-only.
- [ ] Both Part 2 toggles are only active where the tenant's `startup_recognition_enabled` module flag is on for that client/program — same double-gating pattern as Part 1's round toggles.
- [ ] A first-class District level exists in a dedicated `state_master`→`district_master`→`city_master`→`subdivision_master` hierarchy (**resolved 2026-08-07**: City is included as its own segment in this new hierarchy, not left out — see Per-repo plan → backend). Every segment in this hierarchy, City included, is independently hideable/showable via the same setup screens as every other segment/layer (Format Builder for the ID string, Card Design Builder for the printable card) — none is mandatory.
- [ ] Sub-Division is mandatory on the registration form for any startup whose profile form includes the field; a genuinely legacy startup (predating the field's existence on their tenant's form) generates with that segment omitted rather than being blocked.

### tenants (sanchiconnect-saas-tenants)
- Add `startup_recognition_enabled` boolean column to `TenantUsersEntity` (`sanchiconnect-saas-tenants/src/modules/tenants/entities/tenant-users.entity.ts`), default `false`, alongside the existing `startup_id_cards` column at `tenant-users.entity.ts:2126-2132` — **Evidenced**: `startup_id_cards` already exists there (`name: 'startup_id_cards', width: 1, type: 'boolean', default: false`), confirming both the naming convention and that this is a genuinely new, second/parallel flag, not a rename of the old one.
- Backfill existing tenant rows to `false` on migration.
- This is the only tenant-side control for the whole module — no separate "master" toggle is introduced here; the round-level `generate_recognition_id`/`freeze_applications` booleans live on the backend's round entities, not on `tenant_users`.
- **Build-vs-reuse decision — final, confirmed 2026-08-08 (build new)**: **Evidenced 2026-08-07 — reuse assessed and rejected**, and re-confirmed 2026-08-08 rather than reversed: a direct code inspection of `id_card_builders`/`id_cards` (both PHP admin and backend) confirmed the two systems are incompatible at two levels that still hold regardless of anything else in this spec: (1) the existing "ID Number" is a flat `prefix+YYYYMMDD+zero-padded-row-PK` string — the "sequence" is literally the card row's own auto-increment PK, not an independent segment-scoped counter, and has no geography linkage at all; (2) the existing builder is 4 fixed canned layouts (`default/modern/compact/vertical`) with boolean show/hide toggles only — there is no free X/Y layer positioning anywhere in `id_card_builders` or `sc-id-card-renderer`. Rendering is also live Angular DOM only (`angular2-qrcode`), confirmed **no PDF/image generation exists** in the current feature. (The original third differentiator — "tenant self-service vs. platform-operator-controlled" — dissolved on 2026-08-08 when the new module also became tenant self-service, but the two data/design-tool differentiators above are sufficient on their own.)
- **Cutover mechanics — RESOLVED 2026-08-08, supersedes the design-decision-pending entry below**: the "does converging supersede a live tenant's card, run in parallel, or need a deliberate cutover step" question **assumed live production usage that does not exist** — confirmed by the user: **zero tenants currently have `startup_id_cards` turned on**. With no live card scheme or issued IDs to protect, there is nothing to migrate and no cutover to design. Decision: `id_card_builders`/`id_cards`/`startup_id_cards` are **retired going forward** — the code and existing flag are left exactly as they are (no forced removal, no data migration, zero risk of touching something live), but from this point on **no tenant, new or existing, is onboarded onto the old module** for this capability. `startup_recognition_enabled` is the only path offered. Actually deleting the dormant `id_card_builders`/`id_cards` code is a separate, later cleanup task — out of scope here, and not requested.

### backend (sc-saas-backend)
- New `StartupRecognitionIdModule` (mirrors the existing module layout convention — controller/service/dto/entities/repositories, per `sc-saas-backend/CLAUDE.md`'s module map).
- **Entities** (all new, per-tenant DB, no existing equivalents found — **Evidenced** by a full-workspace grep for `StartupId`/`recognition_id`/`startup_recognition_enabled` returning zero code hits before this spec).
- **Resolved 2026-08-07 — schema reconciled against an owner-supplied reference sketch, superseding the single generic `StartupIdLocationEntity` design below for District/Sub-Division specifically**:
  - `state_master` / `district_master` / `subdivision_master` — three **dedicated, FK-linked tables** (District→State, Sub-Division→District), not one polymorphic `type`-enum table. This is a deliberate improvement over the generic-table approach: parent-child integrity is a DB-level FK guarantee instead of app-level validation. Mirrors the existing `states`/`cities`/`countries` module convention in this repo (confirmed at `sc-saas-backend/src/modules/global/states/states.entity.ts` + `states.repository.ts`) — same file layout (`*.entity.ts` + a thin `*.repository.ts`), but with one deliberate improvement the existing pattern lacks: `states.repository.ts`'s `isValidStateId()` only checks bare existence (confirmed by reading it), not parent-chain membership, which the design doc flagged as a real gap for a government-issued ID. `district-master.repository.ts`/`subdivision-master.repository.ts` must implement `isValidDistrictId(districtId, stateId)`/`isValidSubdivisionId(subdivisionId, districtId)` checking the full chain, not just existence.
  - `StandardGeographyEntity` — platform-seeded, read-only reference data (ISO 3166-1/3166-2 + national district codes e.g. India's LGD), seeded per tenant DB at provisioning. `district_master`/`subdivision_master` rows optionally FK to it (nullable) plus a `manual_entry` flag for the fallback path, preserving the original registry-match-vs-manual-entry design against the new dedicated tables. **Resolved 2026-08-07**: must support countries beyond India in the future (not an India-only assumption); an unseeded region falls back to manual entry rather than blocking Startup ID configuration entirely.
  - **This hierarchy is deliberately decoupled from the existing registration cascade** (`registeredCountryId`/`registeredStateId`/`registeredCityId` on `startups`, per the companion design doc's explicit note "kept separate ... different purpose") — District/Sub-Division/City here are Startup-ID-specific reference data, a parallel hierarchy, not an extension of the general registration fields.
  - **`city_master`** (**resolved 2026-08-07 — fully resolves the "District/City hierarchy placement" question**): City is added as its own table, nested under District (`state_master` → `district_master` → `city_master` → `subdivision_master`), mirroring the same FK-linked, parent-chain-validated pattern as the other three tables (`isValidCityId(cityId, districtId)`). City becomes a first-class, independently toggleable segment/bound-field — like every other segment, it is not mandatory: the tenant's own Developer Admin can hide or show the City section specifically on the tenant's card via the Card Design Builder (and, consistently with every other segment, via the Format Builder for the ID string itself) — **updated 2026-08-08**, this was originally written as a platform-operator action before the Admin Portal→`sc-saas-admin` relocation. This does **not** reuse the existing registration `CitiesEntity` (`sc-saas-backend/src/modules/global/cities`) — that stays exactly as-is for its own unrelated purpose, per the decoupling note above. **[INFERRED — requires validation]** the exact nesting order (District→City→Sub-Division here) is a reasonable default, not an explicitly confirmed order — worth a quick sanity check alongside the parent decoupling confirmation.
  - Country Code and State Code segments remain fixed-per-tenant constants set at provisioning (per BRD §6.2) — `state_master` supplies the fixed value and code, it is not re-derived from each startup's own registration state.
  - `StartupRecognitionIdConfigEntity` — one row/tenant, ordered segment list (JSON: segment type + fixed value for Country/State), delimiter, version. Unaffected by this reconciliation — this is the Format Builder's assembly-order config, a separate concern from the geography data tables above.
  - **Hub/Spoke — resolved 2026-08-08, supersedes the earlier `hub_master`/`spoke_master` design entirely.** This is not new reference data at all — it is the **existing ecosystem/partner mechanism**, evidenced end-to-end: tenant flag `ecosystem_enabled` (`sanchiconnect-saas-tenants/src/modules/tenants/entities/tenant-users.entity.ts:611-617`, surfaced via `verify_tenant`/tenant-settings; backend `Feature.ECOSYSTEM_ENABLED` at `enum.ts:1077`); nullable `partnerId` column already on `startups.entity.ts:190-191` (and on every other stakeholder entity — mentor/investor/individual/service-provider/corporate/program-office-member); the existing `partners` table (`sc-saas-backend/src/modules/partner/entities/partner.entity.ts`). **"Hub" has no dedicated entity and never will** — it is purely the absence of a partner (`partnerId IS NULL`); a startup does not get assigned "to the Hub," it simply has no partner. **"Spoke" is `partnerId IS NOT NULL`** — the startup already belongs to one of the tenant's existing `partners` rows.
    - Generation rule (**confirmed by product**): when assembling `recognition_id`, if `Feature.ECOSYSTEM_ENABLED` is true for the tenant **and** the startup's `partnerId` is not null **and** the tenant's saved format includes the Spoke segment, append that partner's abbreviation. If `partnerId` is null (Hub-owned) — **resolved via product decision 2026-08-08, not a fixed literal** — the segment is simply omitted from the assembled code, same omission behavior as every other optional segment with no value, not a placeholder like `"HUB"`.
    - `partners` table currently has **no abbreviation/short-code field** (confirmed by a full-field grep of `partner.entity.ts` — no `abbreviation`/`short_code`/`short_name` match). New: add an `abbreviation` varchar column to `partners`, auto-suggested from the partner's name (first 3 letters, consistent with the original Spoke-naming intent) but editable on the existing Partner add/edit form (`sc-saas-admin/modules/partners/`) — not a new Location Master tab. Unique per tenant.
    - **This collapses the Format Builder's earlier two-segment "Hub" + "Spoke" design into a single segment, "Spoke"** — there was never a second real data value for "Hub" to hold.
    - No new assignment UI is needed anywhere in this feature: a startup already becomes a Spoke through the existing partner self-registration flow (`registerUserProfile.partnerUUID` → `auth.service.ts:907-909`) or the partner-portal's own "add a startup" flow. **Caveat, not part of this feature's scope but directly affects Spoke-detection correctness**: that second flow (`partner.service.ts:438-497` → `createNewStartup()`) currently does **not** set `partnerId` on the startup it creates, unlike `startup.repository.ts:89-101` which supports it — filed separately as **SAN-301** (High, `sc-saas-backend`), not fixed by this spec.
  - `DigitalIdCardTemplateEntity` — one active row/tenant/side (front/back); layer list as JSON. Unaffected by this reconciliation.
  - `startup_recognition_id_sequence` (**resolved 2026-08-07, renamed/simplified from `StartupIdSerialCounterEntity`**) — one row per `state_id` (FK to `state_master`), single `last_serial` column, atomic increment. **No `year` column / no per-year partitioning** — explicitly confirmed continuous, never resets (re-confirming the original BRD §3.1/§9.2 decision after the reference sketch's `year` column raised the question). **Evidenced anti-pattern to avoid**: `specs/features/FA-001-application-evaluation.spec.md:83` documents a real, live race condition in `sc-saas-admin`'s `generateMentorApplicationNo()` using `SELECT MAX(application_no) + 1` with no DB uniqueness constraint — this module must use `INSERT...ON DUPLICATE KEY UPDATE`+`LAST_INSERT_ID` (or an equivalent locking read) instead, exactly as the companion design doc specifies. No hard stop at `999,999` — extends to a 7th (and further) digit; assembly logic must not assume a fixed 6-character serial width.
  - `StartupRecognitionIdRegenerationLogEntity` — append-only audit (actor, timestamp, old/new format snapshot, affected count). Unaffected by this reconciliation.
- **Existing entities modified**:
  - `startups` table (`sc-saas-backend/src/modules/startup/entities/startup.entity.ts`): **resolved 2026-08-07 — flattened onto `startups` directly, superseding the earlier separate `StartupIdEntity` table design**, per the reconciled reference schema:
    - `recognition_id` varchar UNIQUE — **never** `startup_id`/`startupId` (hard naming rule, see below) — the assembled code.
    - `recognition_year` int, `state_id`/`district_id`/`subdivision_id` FK (all nullable — any segment may be excluded from a tenant's format), `serial_no` int nullable.
    - `recognition_suffix` varchar nullable — the collision-safe disambiguating suffix backstop (§9.2/§6.3), needs somewhere to persist even though it's flattened.
    - `recognition_round_id` int nullable — which round triggered generation, needed for the idempotency/audit rule (a startup already holding a Startup ID is never re-generated on a later round entry).
    - `recognition_generated_at`, `recognition_regenerated_at` timestamp nullable, `recognition_regeneration_count` int default 0 — needed for the confirmed format-change regenerate-all audit trail (§7.4).
    - This is a genuine architecture simplification (flat columns vs. a separate one-row-per-issued-ID table) — acceptable because "one active Startup ID per startup, ever" means there is only ever one row to hold anyway; the audit-relevant columns above are preserved so no acceptance criterion from Part 1 is lost by the flattening.
  - `startups` table: **Resolved 2026-08-07 (Sub-Division mandatory/legacy rule)** — once the Sub-Division field exists on a tenant's registration form, it is mandatory and generation blocks until filled in; a startup is only exempt (segment simply omitted from the assembled code) if their profile genuinely predates the field's existence on that tenant's form. This is stricter than the BRD's original framing, which treated omission as the default fallback.
  - Round entities: two new booleans, `generate_recognition_id` + `freeze_applications`, added **only** to the Program Management family — **resolved by product decision (2026-08-07)**, scoping this feature to `ProgramRoundsEntity`/`program_rounds` (`sc-saas-backend/src/modules/program-management/entities/program-rounds.entity.ts`), which is directly keyed to `startupId` via its paired `ProgramStartupRoundsEntity`/`program_startup_rounds` — a clean fit for Startup ID generation with no extra lookup hop. The two sibling families are explicitly **out of scope**: `ApplicationProgramRoundsEntity`/`application_program_rounds` (the "Call for Applications" flow, paired with `ApplicationProgramSubmissionRoundsEntity`, keyed by `submissionId` not `startupId`) and the individual-scoped Venture Studio family (`VsProgramRoundsEntity`/`VsProgramIndividualRoundsEntity`, keyed by `individualId` — not company/startup-scoped, structurally inapplicable to a company-level Startup ID). `program-management.controller.ts`/`.service.ts` is a fully separate code path from `application-program.controller.ts`/`.service.ts` — confirmed no shared round-transition service underneath either — so this decision also means the generation/freeze hook is wired into exactly one service, not duplicated.

### Resolved 2026-08-08 (final batch — last open item closed)

- **`startup_id_cards`/`id_card_builders` cutover — RESOLVED, not by designing a migration but by discovering none is needed.** Confirmed by the user (a business/operational fact, not something derivable from code — **[NOT CODE-EVIDENCED, product-confirmed]**): **zero tenants currently have `startup_id_cards` turned on.** The build-vs-reuse decision itself is unchanged and re-confirmed (build new — the ID-scheme and design-tool incompatibilities evidenced 2026-08-07 hold regardless of live usage). What changes is the cutover question: with no live card scheme or issued IDs anywhere, "supersede vs. run parallel vs. deliberate cutover" was solving a problem that doesn't exist. Decision: **retire `startup_id_cards`/`id_card_builders`/`id_cards` going forward** — untouched in the codebase, simply never offered to a tenant again; `startup_recognition_enabled` is the sole path for every tenant, new or existing, from here on. Actual code removal is an explicit non-goal of this spec (see Out of scope).
- **Confirmed this module is generically tenant-configurable, not built around the Tripura/TRISE reference example.** The reference card (`TR26-GOM-UDPR-000326`) is one tenant's particular configuration of the module, not a hardcoded shape: any tenant can independently choose (a) which segments appear and in what order (Format Builder — Country Code, State Code, Year, District, City, Sub-Division, Spoke, Serial No., any combination, none mandatory), (b) their own District/City/Sub-Division registry (Location Master — matched against the shared platform-seeded `StandardGeographyEntity` or entered manually, scoped per tenant), (c) their own fixed Country/State code (set once at provisioning, per the one-deployment-per-tenant model), and (d) their own card's visual design (Card Design Builder — free-layer canvas, static + bound layers, per tenant). A second tenant with an entirely different segment set, different districts, and a differently-branded card is the same module, zero new code — this was already the design intent from the 2026-08-07 pass, re-confirmed here as the direct answer to "how do we support any client's specific requirement."
