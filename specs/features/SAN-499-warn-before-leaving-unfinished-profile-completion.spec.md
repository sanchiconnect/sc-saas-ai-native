## Problem

Per the BRD "Stakeholder Profile Forms Auto-Save, and Guide Users Instead of Letting Them Wander Off Incomplete": once SAN-497 removed the explicit Save button and SAN-498 blocked skipping ahead to an incomplete step, a user can still freely click away from the profile-completion area entirely (e.g. to another dashboard section) without ever submitting, with no warning at all. Because SAN-497's auto-save already protects against data loss, the goal here is not to prevent data loss but to make sure the user *knows* they're leaving before finishing, giving them a chance to stay and finish instead of wandering off. This issue adds a Stay/Discard confirmation the first time a user tries to leave the profile-completion area for another part of the dashboard, before they've ever submitted.

## Resolved design decision (confirmed with product before this spec, not an open question)

**This warning applies only the first time through, before the user has ever submitted their profile.** Once a user has submitted at least once, returning later to edit does **not** show this leave-warning again, regardless of current completeness (e.g. if they later clear a required field). See Finding 2 below for the concrete signal that implements "has ever submitted."

## Findings (this issue's own investigation, building on SAN-496/497/498)

### 1. Where would a leave-guard actually live, given there's no shared layout wrapping the step components?

**Evidenced — there is no single parent route to attach one guard to per type; the guard must be attached per sibling route, but its own logic can still be one generic, reusable class.**

- SAN-498 already established (its finding 1) that nav-links is embedded as a child *inside* each step component's own template, with no parent layout component. This spec's own check of the **routing config** (not the template-embedding SAN-498 checked) confirms the same flatness one level up: `startups-routing.module.ts:30-196` declares every step — `edit/financial-details`, `edit/industry-technology`, `edit/mentorship`, `edit/pitch-deck-documents`, `edit/product-information`, `edit/startup-information`, `edit/extra`, `edit/custom-forms/:uuid/:slug`, `edit/team`, `edit/pitch-deck/fundraising-pitch`, `edit/pitch-deck/sales-pitch`, `edit/supporting-documents`, `edit/pitch-deck/hiring-pitch`, `edit/hire` — as **14 separate sibling route objects**, all direct children of one shared `ProtectedLayoutWrapperComponent` route (`:32-34`), not nested under a common `path: 'edit'` parent with its own `children` array. `investors-routing.module.ts:37-86` shows the identical flat-sibling pattern (`edit/organization-details`, `edit/investments-details`, `edit/individual-investments-details`, `edit/representative-details`, `edit/individual-details`, `edit/extra`, `edit/custom-forms/:uuid/:slug`). **Consequence: there is no single parent route per type to attach one `CanDeactivate` guard to — it must be attached to every qualifying sibling route's `canDeactivate` array, once per route, for every type** (mirroring the same "per-component, not per-shared-wrapper" cost shape SAN-497/498 already found for save-wiring and tab-gating).
- **No existing `CanDeactivate` guard exists anywhere in this codebase.** `Grep` for `canDeactivate|CanDeactivate` across all of `src/app` returns exactly one hit, and it is fully commented-out dead code: `modules/meetings/pages/meeting/meeting.component.ts:73-78` (`// @HostListener... // canDeactivate(e) {...}`), never wired to any route. All existing guards (`shared/guards/auth.guard.ts`, `shared/guards/disable-startup-profile-update.guard.ts`, `shared/guards/jobcreate.guard.ts`, `shared/guards/non-auth.guard.ts`) implement `CanActivate` only. **This is genuinely new infrastructure for the codebase**, though it follows the exact same established pattern (`@Injectable({providedIn:'root'})`, constructor-injected `Store`/`Router`/services, NgRx `select` + `distinctUntilChanged` subscription for reactive state — see `disable-startup-profile-update.guard.ts:16-32`) that every existing `CanActivate` guard already uses.
- **Distinguishing "still inside the profile-completion area" vs. "leaving it" does not need any new plumbing beyond what `CanDeactivate` already provides.** Angular's `CanDeactivate<T>` interface passes `(component, currentRoute, currentState, nextState)` to the guard — `nextState: RouterStateSnapshot` already carries the destination URL the router is about to navigate to, with no extra wiring needed. A single generic guard can compute "am I still inside the same profile-completion area?" as a plain string-prefix comparison: take `currentState.url`'s path up through the `edit` (or `edit-preview`) segment (e.g. `/startups/edit`, `/investors/edit`) and check whether `nextState.url` still starts with that same prefix. This needs no per-type route `data` and no per-type subclassing — one `UnsavedProfileLeaveGuard` class, attached at every qualifying route, works for all 8 types.

### 2. How to detect "before finishing (before submitting)" and "has ever submitted" — and is it the same field for all 8 types?

**Evidenced — yes, one field, uniformly modeled and behaviorally one-shot on the backend across all 8 types — but the frontend's local copy of it is not reliably kept in sync at the moment of submission, a real bug this spec's own per-repo plan now fixes (see Design decisions, item 2).**

- The shared `profileCompleteness` shape (`core/domain/startup-investor-dashboard.model.ts:57-75`, `StartupProfileCompleteness`) declares `isApprovalRequested: boolean` (`:63`) alongside `canRequestApproval`, `isApproved?`, `isRejected?`. This is the exact field SAN-496 flagged (e.g. `individual-profile-completeness.component.html:55-66`, confirmed to actually live at `service-provider-profile-completeness.component.html:55-66` due to the copy-paste-residue naming SAN-496/498 already documented) gating each type's "Submit" button (`!profileCompleteness?.isApprovalRequested && profileCompleteness?.canRequestApproval && profileCompleteness?.percentage >= 100`).
- **Confirmed present, backend-populated, and named identically for all 8 stakeholder types** — grepped every backend module: `startup.entity.ts:430`, `investor.entity.ts:133`, `individual.entity.ts:110`, `corporate.entity.ts:176`, `mentor.entity.ts:169`, `partner.entity.ts:129`, `program-office-member.entity.ts:137`, `service-provider.entity.ts:142` all declare `isApprovalRequested: boolean`, and each type's `*.repository.ts` copies it 1:1 into its own completeness-report DTO (e.g. `startup.repository.ts:2094-2095`, `investor.repository.ts:1284-1285`, `individual.repository.ts:381-382`, `corporate.repository.ts:646-647`, `mentor.repository.ts:609-610`, `partner.repository.ts:952-953`, `program-office-member.repository.ts:653-654`, `service-provider.repository.ts:708-709`).
- **Confirmed one-shot / never reset back to `false` once true on the backend, for all 8 types** — every type's own `*.service.ts` guards the request-approval action with `if (x.isApprovalRequested) { throw ... }` before allowing another request (`startup.service.ts:1368`, `investor.service.ts:600`, `individual.service.ts:285`, `corporate.service.ts:294`, `mentor.service.ts:322`, `partner.service.ts:596`, `program-office-members.service.ts:233`, `service-provider.service.ts:284`; the `individual` module's own `module.spec.md:52` documents this explicitly: *"Approval request is one-shot: throws ConflictException if isApprovalRequested already set."*). Every `isApprovalRequested: false` hit found in each repository is at **entity-creation time** only — no code path anywhere resets an existing row's `isApprovalRequested` back to `false` after it's been set true (approval and rejection both leave it `true`; only `isApproved`/`isRejected` change). **Backend `isApprovalRequested === true` is confirmed a reliable, permanent, one-shot "has submitted before" signal for all 8 types.**
- **Confirmed real, systemic bug in how the frontend keeps its local copy of this field in sync at the exact moment of submission — checked across all 8 types, not just one.** Every type's own "Submit" success handler follows the same shape: dispatch a `SendRequestApproval` action, then navigate away shortly after (`individual-profile-completeness.component.ts:119-127` — dispatch, then a **hardcoded 1500ms `setTimeout`**, then `router.navigate(...)`; `program-office-profile-completeness.component.ts:139-142`, `mentor-profile-completeness.component.ts:141-144`, `service-provider-profile-completeness.component.ts:137-140`, `corporate-profile-completeness.component.ts:137-140`, `partner-profile-completeness.component.ts:118-121` — same dispatch-then-1500ms-setTimeout-then-navigate shape; `investor-profile-request-approval.component.ts:111-114` — dispatch then navigate with **zero delay at all**, the riskiest of the 8). Traced the actual state update for one representative type (`mentors-dashboard`, same shape confirmed across the others by the identical action/reducer naming convention): `mentors.dashboard.effect.ts:35-43`'s effect for `SendRequestApproval` only ever dispatches `SendRequestApprovalSuccess(data)` — it never dispatches a `GetProfileCompleteness()` refetch. `mentors.dashboard.reducer.ts:92-98`'s `initRequestApproval()` (run synchronously on the initiating `SendRequestApproval` dispatch, before any API call resolves) only sets `requestApprovalLoading: true` — it does **not** touch `state.mentorProfileCompleteness` at all. **Net effect: the NgRx-store copy of `profileCompleteness.isApprovalRequested` is never updated as part of the submit flow, at any point, for any type** — it would only become `true` in the store the next time something happens to re-dispatch `GetProfileCompleteness()` (e.g. a future full page load), which is not guaranteed to happen before the post-submit `router.navigate()` fires (and for investor-org, is definitely not happening in time — zero delay). Left unfixed, this would make the new leave-guard show a spurious Stay/Discard prompt immediately after a user legitimately submits, for all 8 types — not a rare race, a near-certain one. **Resolved as a required per-repo-plan fix, not left as a residual risk — see Design decisions, item 2.**

### 3. UI pattern for the Stay/Discard prompt

**Evidenced — a genuine two-choice SweetAlert2 confirm/cancel pattern already exists in this codebase and is directly reusable; no new UI library needed.**

- `ToastAlertService.showCenteredAlert()` (`shared/utils/toast.service.ts:47-53`, added by SAN-498) is **confirm-only** — `Swal.fire({ icon, text: message, confirmButtonText: 'Ok' })`, no `showCancelButton`. It is not sufficient as-is for a real two-choice prompt.
- A genuine two-choice `Swal.fire({ showCancelButton: true, ... })` confirm/cancel pattern is already used elsewhere, e.g. `modules/connection-v4/connection-v4.component.ts:421-433` ("Remove connection" — `showCancelButton: true`, `confirmButtonText: 'Yes'`, checks `result.isConfirmed` to proceed) and `individual-profile-completeness.component.ts:86-115` (the Submit-confirmation dialog itself uses `showCancelButton: true` plus `showDenyButton: true` for a three-way Submit/Preview/dismiss choice). `sweetalert2` is already a project dependency, already imported directly in components (not only through `ToastAlertService`).
- **No existing usage of `focusCancel`/`reverseButtons`** (grepped, zero matches) — SweetAlert2 defaults to focusing the *confirm* button and rendering it first. Since the AC requires "Stay" to be the primary/default choice, this issue needs to add: `showCancelButton: true`, `confirmButtonText: 'Discard'`, `cancelButtonText: 'Stay'`, `focusCancel: true` (keyboard Enter / default focus goes to "Stay"), and `reverseButtons: true` (renders "Stay" in the visually primary/first position) — a small, well-precedented config addition on the existing pattern, not new UI infrastructure. Map `result.isConfirmed` (Discard clicked) → resolve the `CanDeactivate` guard `true` (allow navigation); any other outcome — "Stay" clicked, backdrop click, or Escape — → resolve `false` (block navigation, stay exactly where the user was, per the AC). Treating backdrop/Escape as "Stay" (the safe default) rather than as an implicit Discard matches the "Stay is the default" requirement and avoids a user accidentally leaving by clicking outside the modal.
- Recommended location: extend `ToastAlertService` with a new method (e.g. `showLeaveConfirm(message): Promise<boolean>`) wrapping the above, rather than inlining `Swal.fire` directly in the new guard — keeps the guard itself UI-agnostic and matches how `showCenteredAlert()` was added as a service method in SAN-498, not inlined at the call site.

### 4. Coverage scope — broader than SAN-497/498's precedent, and that's the right call here

**Evidenced — the guard's own mechanism (a route-level `CanDeactivate`, gated only by "same edit-area prefix or not") naturally covers every route under a type's edit area at zero extra marginal cost, unlike SAN-497/498 which each had a real per-step-component technical reason to scope down to the 9 primary steps.**

- SAN-497 scoped to the 9 primary steps + `EventFormsComponent` because save-wiring is a per-component, per-service-call concern — secondary tabs' own Save-button presence was simply unaudited (SAN-497's decision 3, explicit follow-up candidate). SAN-498 scoped the same way because its guard reads per-tab completeness data that had to be ported into specific nav-links components.
- **Neither constraint applies here.** This issue's guard doesn't care which step is mounted, what its own save mechanics are, or whether it renders a nav-links completeness icon — it only asks "is the navigation target still under this type's own `/…/edit` path prefix, or not?" That check is identical and equally cheap for *every* route in a type's routing config, including the "secondary/non-primary" ones SAN-497/498 explicitly deferred (Startup's `edit/team`, `edit/hire`, `edit/supporting-documents`, `edit/pitch-deck/*`; the equivalent secondary tabs for the other 7 types).
- **Decision: attach the guard to every real edit-area route for each of the 8 types** (i.e. broader than SAN-497/498's primary-step scope, and explicitly so) — not just the 9 primary-step-family routes. This also automatically covers tenant-admin custom-form tabs, since (per finding 1) `edit/extra` and `edit/custom-forms/:uuid/:slug` are ordinary sibling routes under the very same prefix, exactly like every other step.
- **Not covered, and correctly so:** the `edit-preview/*` route family (`startups-routing.module.ts:205-262`'s `formPreviewRoutes`, mounted under `AuthLayoutWrapperComponent` with `data: { preview: true }`) — this is a separate, non-authenticated-user preview surface (tenant-admin/design-time form preview), not a real user's own in-progress profile-completion journey, and has no submission concept. Out of scope.

## Design decisions (resolved 2026-08-24)

Both prior open questions are resolved as follows:

1. **Browser Back/Forward carve-out — build a popstate detector, using Angular Router's own navigation-trigger metadata (not a hand-wave "detect popstate").** Confirmed mechanism: every Angular Router navigation emits a `NavigationStart` event (`@angular/router`) carrying a `navigationTrigger: 'imperative' | 'popstate' | 'hashchange'` property, and this event fires before any guard (`canDeactivate`/`canActivate`) runs in the navigation pipeline (`NavigationStart` → `RoutesRecognized` → `GuardsCheckStart` → ... → `GuardsCheckEnd`) — confirmed against the Angular 13.3 (`package.json:22`, `"@angular/core": "~13.3.0"`) Router's documented event ordering. `Router.events` subscription is already an established pattern in this codebase (`app.component.ts:82-90` subscribes for `NavigationEnd`; five other components subscribe similarly), but nothing today reads `navigationTrigger`. **Concrete implementation:** add a new root-provided singleton, `shared/utils/navigation-trigger.service.ts` (`@Injectable({providedIn:'root'})`), that subscribes to `router.events.pipe(filter(e => e instanceof NavigationStart))` in its constructor and stores the latest `event.navigationTrigger` on a plain instance property (e.g. `lastTrigger`). Because `NavigationStart` always precedes guard checks for the *same* navigation attempt, `UnsavedProfileLeaveGuard.canDeactivate()` can synchronously read this service's `lastTrigger` and, if it's `'popstate'`, resolve `true` immediately — letting the browser Back/Forward navigation through silently, with no Stay/Discard prompt, no dialog, no side effect. `'imperative'` (in-app link clicks, `router.navigate()` calls) and `'hashchange'` (not used by this app's routing) continue through the existing isApprovalRequested + same-prefix logic (findings 1–2). This uniformly satisfies the AC's literal grouping of "browser back/refresh/close/direct-URL" as out of scope for all 4 cases: refresh/close/direct-URL already never reach `CanDeactivate` at all (full page navigation bypasses the Angular Router entirely, per the existing Contracts & invariants note below), and this carve-out now excludes the one remaining case (in-SPA Back/Forward) that otherwise would have been guard-observable.
2. **The frontend-state-sync bug found in finding 2 is a required fix in this issue's own per-repo plan, not a residual risk left for later.** For each of the 8 types' own dashboard reducer (mirroring `mentors.dashboard.reducer.ts:92-98`'s `initRequestApproval()`), add `isApprovalRequested: true` to that type's own in-memory `*ProfileCompleteness` object **synchronously, on the initiating `SendRequestApproval` action itself** (not only after `SendRequestApprovalSuccess` resolves from the network) — e.g. `initRequestApproval(state)` returns `{ ...state, mentorProfileCompleteness: state.mentorProfileCompleteness ? { ...state.mentorProfileCompleteness, isApprovalRequested: true } : state.mentorProfileCompleteness, requestApprovalLoading: true, requestApprovalError: '' }`, applied analogously for the other 7 types' equivalent reducers. Because NgRx `dispatch` → reducer update is synchronous, and every type's own submit-confirm handler already dispatches `SendRequestApproval()` as the very first step inside its `Swal.fire().then()` callback (before any `setTimeout`/`router.navigate()`), this guarantees the store's `isApprovalRequested` reads `true` by the time the leave-guard (or anything else) checks it — deterministically, independent of network latency, and covering even investor-org's zero-delay navigate. This is a targeted fix to the exact 8 reducer functions already named in finding 2, not a broader refactor of the approval flow.
3. **Assignee: Mahima Sharma** (matches SAN-496/497/498), for the whole project (single-repo scope).

## Acceptance criteria

- [ ] A user who has never submitted their profile (`profileCompleteness.isApprovalRequested !== true` for their stakeholder type, finding 2) and who clicks any in-app link/navigation control that would take them outside their type's profile-completion edit-area (i.e. the destination URL no longer starts with that type's own edit-area route prefix, finding 1) sees a centered Stay/Discard confirmation before the navigation completes.
- [ ] The prompt offers exactly two choices: "Stay" (primary/default — has default keyboard focus and is not the destructive action) and "Discard" (proceeds with leaving).
- [ ] Choosing "Discard" completes the navigation to wherever the user originally clicked; it does not delete, reset, or resubmit any already-entered data (SAN-497's auto-save already covers persistence — this issue's own code makes no save/delete call).
- [ ] Choosing "Stay", dismissing via backdrop click, or dismissing via Escape all leave the user exactly on the page they were on, with the attempted navigation cancelled and nothing they'd entered disturbed.
- [ ] Navigating between steps/tabs *within* the same type's own profile-completion area (including the tenant-admin custom-form tabs, finding 4) never shows this prompt, regardless of completeness — this issue only gates leaving the area entirely, never in-area movement (that is SAN-498's job, unaffected by this issue).
- [ ] Once a user's `profileCompleteness.isApprovalRequested` is `true` for their type (they have submitted at least once, ever), this prompt never shows again for that user, regardless of later edits or completeness regressions (resolved design decision, above) — including immediately after the submit action itself, not just on a later visit (design decision 2's reducer fix).
- [ ] Browser Back/Forward button clicks are detected via `NavigationStart.navigationTrigger === 'popstate'` (design decision 1) and let through with no prompt, no dialog, and no side effect. Refresh, tab close, and direct-URL navigation are not the target of this issue's mechanism at all — `CanDeactivate` does not run for a full page reload/close/direct-URL entry, since those bypass the Angular Router entirely.
- [ ] No new backend endpoint, DTO, or flag is introduced; the guard reads the same `profileCompleteness$` stream/data already fetched today (SAN-497/498), and the confirm dialog is pure frontend UI.

## Contracts & invariants

- **Flags:** none touched.
- **API:** none touched — no new endpoint or DTO; reuses the existing `profileCompleteness` payload already fetched today for nav-links/top-bar widgets (SAN-497/498).
- **Events:** none.
- **Invariants at risk:** none of the 6 hard workspace invariants are implicated — no flag name, API/DTO, tenant-verification-shape, auth-model, or PowerPitch change; invariant #5 (tenant scoping) is not newly at risk since no new query/write is added, only a client-side navigation guard reading data already scoped and fetched today.
- **Architectural nuance, now resolved (design decision 1):** Angular's `CanDeactivate` guards run for *any* Router-mediated navigation while the SPA is still loaded — including in-SPA browser Back/Forward button clicks (`popstate`), which the Router still processes through its full guard pipeline — but they do **not** run for a full page reload, tab close, or a URL typed directly into the address bar, since those bypass the Angular Router entirely. The popstate carve-out (design decision 1) closes this gap so all four browser-level cases the issue calls out are uniformly excluded.
