# AI Credits System — Cross-Repo Wallet, Purchase & Consumption

## Problem

The AI Credits system — a prepaid, per-tenant credit wallet that bills tenants for AI-analyzer usage (scoring, re-score, thesis generation) and lets them top up via Easebuzz — is fully built and in active use across three repos, but has **zero spec documentation anywhere**: no `module.spec.md` exists in `sanchiconnect-saas-tenants/src/modules/ai-credits/`, `sc-saas-admin/modules/ai_credits/`, or `sanchiconnect-saas-tenants-admin/modules/ai_credits/` (confirmed by direct inspection of all three directories), and no workspace-level feature spec exists in `specs/features/` (confirmed against all 25 existing entries prior to this one). `sc-saas-admin/knowledge.md` already contains an accurate, code-verified account of the reserve→settle→refund lifecycle, but it isn't a spec and isn't cross-linked from the other two repos.

This matters beyond documentation hygiene because the as-built architecture is riskier than it looks: `sanchiconnect-saas-tenants` (NestJS/TypeORM) owns the schema for `ai_credit_wallets`, `ai_credit_ledger`, `ai_credit_packages`, `ai_credit_orders`, `ai_credit_transactions`, `ai_credit_invoices`, `ai_credit_grants`, and `ai_credit_task_rates` — but it only ever mutates these tables on the **purchase** path (Easebuzz webhook → `handleEasebuzzCallback()`, `ai-credits.service.ts:267-631`). Every other mutation — reserve, settle, refund, instant-debit (billing), and grant issuance — happens via **direct Medoo/raw-PDO writes from two independently-deployed PHP repos** (`sc-saas-admin`'s `includes/ai_credits_functions.php` and `sanchiconnect-saas-tenants-admin`'s `modules/ai_credits/{grants,packages,task_rates}.php`) against the same shared tenants MySQL database, entirely bypassing TypeORM validation. This is the same dual-writer shape already flagged as a known-issue pattern in `FT-004` (IP & Facility Hub), except with **three** writers instead of two, and it has never been named as a cross-repo contract anywhere.

This spec documents the as-built system as the canonical source of truth (closing the module-spec gap in all three repos), names the 3-writer contract explicitly, prescribes one concrete, uncontroversial hardening fix (a silent Easebuzz-hash failure mode), and surfaces the genuinely open commercial/architecture decisions that must be resolved — not guessed at — before this spec can be approved.

**Evidence-strength key used below:** Evidenced = cited to a real `file:line`. `[INFERRED]` = reasonable extrapolation, not directly stated in source. `[NOT SPECIFIED IN SOURCE]` = a real gap. `[DESIGN DECISION PENDING]` = a new decision with no precedent.

- [ ] The new `sc-saas-admin` module spec documents the "stuck reservation" limitation as a known, named gap: an analysis run whose credits are reserved (`analysis_list.php:171-211`) but that is never finalized (`analysis_result.php`'s first-view settle path) nor archived (`analysis_list.php`'s `deleteAnalysis` refund path) leaves `reserved_balance` outstanding indefinitely, since no scheduled sweep/TTL exists to reclaim it.

## Contracts & invariants

- **Flags:** `ai_credits_enabled` (tenants-owned, `TenantUsersEntity`) is the only flag this system introduces. It gates access to the `sc-saas-admin` `ai_credits/*` UI and every reserve/settle/debit call site in `application_management/*` (`$brandSettings['ai_credits_enabled']`, `config.php:278-279`). It is correctly declared (invariant #1) in `sc-saas-backend`'s `Feature` enum even though backend never reads it — not a violation, just an unused-but-correctly-named entry.
- **API:** All 7 routes listed in `contracts.api` are owned by `sanchiconnect-saas-tenants`. `sc-saas-admin` calls exactly one of them over HTTP (`POST api/v1/ai-credits/purchase`, from `modules/ai_credits/buy.php:127-147`, via cURL with `X-Internal-Api-Key`); every other interaction `sc-saas-admin` and `sanchiconnect-saas-tenants-admin` have with this system's data is a direct Medoo/PDO query against the shared tenants DB, not an API call. Any future NestJS controller/DTO change to the purchase route must be checked against `sc-saas-admin/modules/ai_credits/buy.php`'s cURL payload (invariant #2 applies to this one route only).
- **Events:** None.
- **Invariants at risk:**
  - **#5 (tenant scoping)** — every ai-credits table is scoped by a `domain` string column, the same pattern `tenants` itself uses (not a per-tenant separate DB). NestJS queries are correctly domain-filtered. The risk is that `sc-saas-admin` and `sanchiconnect-saas-tenants-admin` each independently re-implement that same domain filter in raw SQL with no shared enforcement layer — `grants.php` was deliberately hardened to validate submitted domains against real `tenant_users` rows before crediting a wallet (`grants.php:83-104`), but this is a per-file discipline, not a structural guarantee.
  - **Auth model** — two independent layers guard the purchase/webhook/invoice routes: `InternalApiKeyGuard` (opt-in, fail-open when `AI_CREDITS_INTERNAL_API_KEY` is unset, `internal-api-key.guard.ts:23-27`) and, for the two webhook routes only, a mandatory Easebuzz HMAC-SHA512 signature check (`verifyEasebuzzCallbackHash()`) that always runs regardless of the guard's configuration. Changing either layer without understanding the other risks either weakening a real cryptographic check or assuming a shared-secret check is enforced when it silently isn't.
  - **Two Easebuzz configurations exist and are architecturally isolated — confirmed 2026-07-17, traced against external gaps-register item D-2.** The platform-level config used here (`PLATFORM_EASEBUZZ_KEY`/`PLATFORM_EASEBUZZ_SALT`/`PLATFORM_EASEBUZZ_ENV`, a single global env-var-sourced account read by `AppConfigService` in `sanchiconnect-saas-tenants`, used only for AI-Credit top-ups) is structurally distinct from the tenant-level Easebuzz gateway `sc-saas-backend` uses for regular tenant payments (`PaymentGatewaysEntity`, one DB row per tenant deployment, read via `EasebuzzService.setupClient()` → `paymentGatewaysRepository.getGatewayDetails(mode, 'easebuzz')`). Different repos, different storage mechanisms (env var vs. per-tenant DB row), different code paths — no path exists for one to populate the other.
    **Provisioning, confirmed by the team (2026-07-17):** `PLATFORM_EASEBUZZ_KEY`/`SALT`/`ENV` are injected via Jenkins into the `sanchiconnect-saas-tenants` dev/production environment — a single CI-managed value per environment, shared across every tenant's AI-Credit purchases. This is a categorically different provisioning channel from the tenant-level gateway, which is entered per-tenant through the `sc-saas-admin` finance-management UI and stored as a DB row. The two configs aren't just architecturally separate — they're provisioned through entirely different administrative pathways, which makes an accidental same-account collision unlikely in practice, not just in theory. The one thing that still requires a manual check, not derivable from either code or this provisioning fact: whether the *literal key/salt values* in Jenkins happen to match any tenant's stored `payment_gateways` row — that would require comparing the actual Jenkins-held credential against the DB value for a given tenant, which is outside what either codebase or this spec can verify on its own.
  - **Not one of the 6 numbered invariants, but the same shape as invariant #2/#3's "single owner" principle** — the **3-writer architecture**: `sanchiconnect-saas-tenants` (TypeORM) is the nominal schema owner, but `sc-saas-admin` and `sanchiconnect-saas-tenants-admin` both mutate the same rows directly. A TypeORM column rename/type change in `sanchiconnect-saas-tenants` can silently break both PHP repos' raw SQL simultaneously, with no compile-time or CI signal in either PHP repo (mirrors the `FT-004` dual-writer finding for patents/facilities, but with a third writer).

## Rollout

Documentation-only changes (the three `module.spec.md` files) ship independently per repo with no coordination needed and no flag. The one code change prescribed (the Easebuzz fail-fast guard in `sanchiconnect-saas-tenants`) is a backward-compatible tightening — it only changes behavior in an environment where `PLATFORM_EASEBUZZ_KEY`/`PLATFORM_EASEBUZZ_SALT` are already unset, which is already a broken purchase path today. No schema migration, no new flag, no new tenant-facing behavior in this spec.

## Out of scope

- Consolidating the 3-writer architecture behind new NestJS endpoints (e.g., `/reserve`, `/settle`, `/refund`, `/grant`) that `sc-saas-admin`/`sanchiconnect-saas-tenants-admin` would call instead of raw SQL — a real option this spec's findings surface, but a significant architectural change needing its own decision and its own spec (see Open questions).
- A stale-reservation sweep/TTL job for abandoned analysis runs — named as a known limitation, not built here.
- Making `AI_CREDITS_INTERNAL_API_KEY` mandatory (removing `InternalApiKeyGuard`'s fail-open branch) — named as a known risk, not changed here.
- Any change to the commercial model, package pricing, task-rate defaults, or currency/localization policy.
- `ai-startups-analyzer`, `sc-saas-backend`, `sc-saas-frontend` — confirmed to have no functional AI-Credits code; no work items.

## Open questions

**Must-resolve before this spec is approvable:**
- Is the 3-writer architecture (NestJS as schema owner, two PHP repos writing directly via raw SQL) the accepted permanent design, or should reserve/settle/refund/grant be consolidated behind new NestJS endpoints? This determines whether the per-repo plan above is this spec's final shape or only its documentation phase. `[DESIGN DECISION PENDING]`
- Is there a canonical commercial/pricing model to adopt? Today packages and task-rates are entirely operator-discretion via `sanchiconnect-saas-tenants-admin` CRUD, with no approved price list, margin target, or currency policy. (USD billing itself is resolved — see Resolved section below.) `[DESIGN DECISION PENDING]`
- **Expanded 2026-07-17, traced against external gaps-register item P-5:** this is more fundamental than a pricing/currency question — the platform hasn't stated **what kind of commercial system this is meant to be at all**: metered billing with a real revenue/margin target, a soft usage cap with no revenue intent (purely cost control against LLM API spend), or a time-boxed pilot. The as-built system is compatible with any of the three; nothing in code or documentation commits to one. Also unresolved: no seed/default catalogue exists in code (checked — unlike other config tables in this workspace with hardcoded seed defaults, `ai_credit_packages`/`ai_credit_task_rates` have none), so there is no "confirmed catalogue and rates" this spec can cite — current package/rate values are entirely live, operator-entered database rows outside what a code-only review can report. `[DESIGN DECISION PENDING]`
  - **Found while checking rate values, external gaps-register item P-6, not previously documented — Task Rates UI exposes a Phase 2 feature before its backend exists.** The Task Rates admin UI's "Rate Mode" field offers **"Cost multiplier"** as a selectable alternative to "Fixed per unit" (footer copy: *"credits scale with actual LLM USD cost"*), and the schema has the columns to back it (`rate_mode`, `cost_multiplier`). **Team confirmed (2026-07-17): this is an intentional Phase 2 feature, not abandoned functionality** — the schema and UI option were built ahead of the Phase 2 backend work that will implement cost-based charging. The live issue is narrower than "this is dead": because the option is already selectable today, an operator could pick "Cost multiplier" for any task type *before* Phase 2 ships. Every reserve/settle call site in `sc-saas-admin/includes/ai_credits_functions.php` (`analysis_list.php:185-188`, `:559-560`, and the `analysis_result.php` equivalents) computes the charge as `credits_per_unit × applicant_count` **unconditionally** — `rate_mode` is never read and `cost_multiplier` is never consumed yet — so selecting it today silently produces flat-rate billing with no indication the mode isn't active. Tracked as Linear SAN-21: likely fix is to disable/hide "Cost multiplier" in the UI until the Phase 2 backend ships, rather than removing it outright; full cost-based charging implementation is the actual Phase 2 deliverable, tracked separately.
- Should `AI_CREDITS_INTERNAL_API_KEY`'s fail-open default be tightened to fail-closed now that both `sanchiconnect-saas-tenants` and `sc-saas-admin` are live in production, or is the opt-in rollout window still needed in some environment? **Provisioning confirmed by the team (2026-07-17):** like `PLATFORM_EASEBUZZ_KEY`, this value is also injected via Jenkins into the dev/production environment, not left to a checked-in `.env` — meaning the fail-open branch is not actually being exercised in any real environment today; the key is always present where it matters. This resolves the factual "is it ever actually unset in practice" question, but not the design decision itself: whether to now remove the fail-open branch in code (tightening the guard so a future misconfiguration can't silently disable it) is still Sanchi's call to make. `[DESIGN DECISION PENDING]`

**Resolved (team decision, 2026-07-17 — traced against external gaps-register item K-1):**
- **Credit expiry: no expiry implementation planned for now, no rules to define.** K-1 originally claimed "packages carry `valid_days` and the ledger has expiry/refund entry types" — that premise was already confirmed false as built (`ai_credit_packages` has no expiry/validity column at all; neither `AiCreditType` nor `AiLedgerSourceType` has an EXPIRE value; the one real expiry field, `ai_credit_grants.expires_at`, is never enforced anywhere). The team has now confirmed this isn't an oversight to fix — credit expiry is explicitly out of scope for the current phase. No consumption-ordering or expiry-window design is needed until expiry itself becomes a real requirement.
- **Refund policy: confirmed as "refund on analyzer failure" — matches existing behavior.** The team's stated rule is: if the analyzer run fails, the reservation is refunded. This is already what the code does, confirmed at three call sites: a dispatch failure right after reserving (`analysis_list.php:282,297`), an analysis deleted/archived while still holding an unsettled reservation (`analysis_list.php:703`), and a rescore dispatch failure (`analysis_result.php:804`) — all three call `refundAiCreditReservation()`. No broader refund policy (partial refunds, time windows, reversing a completed/settled charge) is needed, since none was asked for. Note this is distinct from the separate, still-open crash-recovery gap below (K-2) — that's about a process dying *mid-flight* with no explicit failure signal, not an analyzer run that fails cleanly and is caught.
- **USD billing: intentionally dormant, not dead weight.** Team confirmed (2026-07-17): `ai_credit_packages.price_usd` is unused today purely because the platform is on Easebuzz, which this system only ever calls for INR charges (`sc-saas-admin/modules/ai_credits/buy.php`) — not because USD billing was abandoned. If the payment gateway changes to one that supports USD, USD billing will be implemented at that point. The column should **not** be dropped from the schema/UI — it's a deliberate placeholder tied to a future gateway decision, not dead code.
- **Task-rate values (the "10 vs 50" question, external gaps-register item P-6): the sprint-planning document's proposed 50 is not authoritative.** Team confirmed (2026-07-17): `ai_credit_task_rates.credits_per_unit` is intentionally managed dynamically, at runtime, via `sanchiconnect-saas-tenants-admin`'s Task Rates screen — there is no fixed "correct" value to migrate to, and no 10→50 migration is planned. The live value (10 credits/unit for AI Analysis, confirmed 2026-07-17) is the current operator-set rate, changeable at any time through the existing admin UI with no code change. The Cost Multiplier no-op bug found alongside this (SAN-21, above) is unrelated to this decision and remains open.

**Deferrable (tracked, do not block approval):**
- **No reserve→settle crash-recovery mechanism exists.** `settleAiCredits()`'s atomicity is solid (claims the RESERVE ledger row first via a checked `rowCount()`, then deducts the wallet inside one transaction — confirmed by direct read of `ai_credits_functions.php:103-186`), but nothing reconciles a reservation left orphaned by a mid-flight process death (analyzer crash, PHP worker killed, etc.) between `reserveAiCredits()` and either `settleAiCredits()`/`refundAiCreditReservation()`. Confirmed no cron/sweep/TTL infrastructure exists anywhere in `sanchiconnect-saas-tenants` or `sc-saas-admin`'s ai-credits code path — recovery today only happens if an operator manually re-opens the result page (settle) or deletes the analysis (refund). Two candidate mechanisms, either would close this: (a) a **timeout-based sweep job** (cron, e.g. in `sc-saas-backend/src/core/cron/` or a new `sc-saas-admin` CLI script) that refunds any RESERVE ledger row older than N hours with no matching DEBIT/REFUND, or (b) an **on-demand reconciliation check** triggered the next time that tenant's wallet/analysis list is viewed. Should one be built, and which?
- `estimateAiCredits()` in `sc-saas-admin/includes/ai_credits_functions.php` is dead code (defined, never called — every real call site inlines the same multiplication) — clean up or leave as documented-but-unused?
