## Problem

Per the BRD "Stakeholder Profile Forms Auto-Save, and Guide Users Instead of Letting Them Wander Off Incomplete," SAN-496 found that every stakeholder type already has a persistent, always-visible "Submit" action in its top-bar completeness widget, separate from the bottom Previous/Next Step bar. This issue moves that Submit action onto the last **primary** page of each type's profile-completion form, in the position "Next Step" occupies, and removes the persistent top-bar Submit (button *and* its auto-popup trigger) once the new one exists.

## Findings (this issue's own investigation, building on SAN-496/497)

### 1. Scope decision: "last page" = last PRIMARY step, not literally the last `navlinks.ts` entry

**Resolved design decision (product/Nirmal, 2026-08-24).** An earlier draft of this spec found that for 5 of 8 types, the true last entry in `PROFILE_NAV_LINKS` order is a secondary/flag-gated tab SAN-497 explicitly deferred (its decision 3 / Out-of-scope list) — e.g. Corporate's "Engagement" (`corporates_enagement_form`), Mentor's "Domain Expertise" (`mentor_domain_expertise_tab`), Partner's "Industry/Technology" (`industries_technologies_section`), Investor org's "Representative Details", and the Investor-individual variant's "Investment Thesis" — each of which still carries its own live Save (or Save-behaving, mislabeled "Submit") button today, untouched by SAN-497.

**Decision: this issue's scope is pinned to the same 9 primary-step components SAN-497/498/499 already work in** — `startup-information`, `individual-profile-edit-form`, `organization-details` (Investor org), `individual-investor-edit-form` (Investor individual variant), `corporate-intro`, `mentor-intro`, `partner-intro`, `service-provider-intro`, `program-office-intro` — consistent with SAN-497/498/499's own established scoping. The 5 types' true-last secondary/flag-gated tab (and its own live Save/mislabeled-Submit button) is **not** touched here; it remains the same standing follow-up debt SAN-497's decision 3 already flagged (see Out of scope). This also means the Submit button's position is now unambiguous and static per type — no flag-dependent "two possible last pages" problem, and no need to touch either of the two shared, multi-purpose step components (`pitch-deck-management`, used by Startup's Pitch Deck plus two unrelated non-navlinks routes; `investments-details`, used by both Investor org's non-last "Investment Details" step and the Investor-individual variant's own last step) — both are entirely out of this issue's file list as a direct consequence of this decision.

**Documented consequence, not a re-opened question:** for the 5 types whose true-last navlinks entry is a secondary/flag-gated tab, that tab remains reachable only via its own nav-link tab click, not via "Next Step" from the primary step (which now shows Submit instead) — so those pages' own leftover Save/mislabeled-Submit buttons are unaffected and un-migrated by this issue, exactly as before it shipped.

### 3. Shared-component extension design (resolved architecture)

**Resolved design decision (product/Nirmal, 2026-08-24): extend `FormNextStepButtonComponent` rather than hardcoding a Submit button per primary-step template.** Concrete design:

- **New `@Input() isLastPrimaryStep = false;`** — mirrors how `disableNavigation` already works (an `@Input` the *embedding* step component sets, not something the shared component infers). Set to `true` only at the live (non-commented-out) `<app-form-next-step-button>` embed site(s) inside each of the 9 primary-step templates; every other embed site across the app (secondary tabs, custom-form wrappers, preview pages — 20+ other sites per SAN-498's own count) is left unchanged and defaults to `false`, so nothing else in the app is affected.
- **New `@Input() submitDisabled = false;`** — a second, independent gate from `disableNavigation` (which reflects the *current step's own form validity*; `submitDisabled` reflects the *type's whole-profile completeness threshold* — a different signal, per Finding 2's per-type table). Computed by each primary-step component itself from a **newly added** subscription to that type's own `profileCompleteness$`/`canRequestApproval` selector (a dependency these 9 files don't currently have — today only the top-bar widgets subscribe to it).
- **New `@Output() submit = new EventEmitter<void>();`** — mirrors `@Output next`. `FormNextStepButtonComponent` stays fully generic: it does not know about `checkAndShowModalForSubmitProfile()`, per-type Swal copy, or per-type dispatch/navigate — it only renders a `<button [disabled]="submitDisabled" (click)="submit.emit()">Submit</button>` in place of "Next Step" when `isLastPrimaryStep` is `true`, using a native `[disabled]` binding (matching how every existing top-bar Submit button already gates itself today, rather than the click-then-toast pattern `disableNavigation`/Next-Step uses) so the relocated button's disabled/enabled visual behavior is identical to today's.
- **Template branch:** when `isLastPrimaryStep` is `true`, render Submit instead of Next Step, unconditionally (not gated by `CommonService.getNextRoute()` / `buttonVisible` at all) — this is what makes decision 4 (custom-tab position, below) automatic: Submit's presence and position no longer depends on what else follows in `editPageLinks`.
- **Per-type wiring in each of the 9 primary-step components:** bind `[isLastPrimaryStep]="true" [submitDisabled]="submitDisabled" (submit)="onSubmitProfile()"` at each live embed site, and **move** (not duplicate) that type's own confirm-modal + dispatch + navigate logic from its top-bar widget into a new `onSubmitProfile()` method on the primary-step component, reusing the exact same Swal config, action dispatch, and post-submit navigation target found in Finding 2 — including Startup's distinct `onRequestApproval()`/`isSubmitDisabled` shape and Investor's per-variant branch (each of the two Investor primary-step files only needs its own half of `investor-providing-funds-switch.component.ts`'s existing org/individual branch, since each file already knows which variant it is).
- **Auto-popup suppression (decision below) folds into the same move:** since the method is being moved out of the widget entirely, the widget's own auto-fire call site (Finding 2's right-hand column) is deleted along with it, not reintroduced anywhere — Submit becomes a purely explicit, click-triggered action on the primary step, for all 8 types (including the 6 that had a live auto-popup before).

### 4. Auto-popup suppression: resolved, not relocated

**Resolved design decision (product/Nirmal, 2026-08-24).** "Suppress the auto-popup" means the on-mount auto-fire behavior is removed outright, not relocated to fire automatically when the primary step mounts. Concretely: the `if (localStorage.getItem('approval-modal') !== 'hide') { this.checkAndShowModalForSubmitProfile(); }` call site (Finding 2's 6 live instances, plus Startup's dead one) is deleted as part of moving `checkAndShowModalForSubmitProfile()`/`onRequestApproval()` out of each widget — it does not get re-added inside the primary-step component. After this issue ships, every type's Submit action is exclusively a deliberate button click on the last primary step; no type auto-pops a confirmation modal on page load anymore. This is a real, intentional behavior change for the 6 types that had a live auto-popup today (Individual, Corporate, Mentor, Partner, Service Provider, Program Office) — called out explicitly here rather than left implicit.

### 5. Tenant custom-form tabs: resolved position

**Resolved design decision (product/Nirmal, 2026-08-24).** The new Submit button appears right after the primary step regardless of whether the tenant has custom-form tabs configured — it marks "the core profile is done"; any custom-form tabs still come after it in the nav-links list, but they no longer sit "in front of" Submit the way a custom-form tab would have pushed out where `buttonVisible`'s dynamic `getNextRoute()` check used to land (Finding 2 of the draft revision). Mechanically this is automatic once `isLastPrimaryStep` is a static `@Input` (Finding 3) rather than derived from `CommonService.getNextRoute()` — Submit's presence stops depending on `editPageLinks` contents at all.

### 6. Revised file-count estimate (recalculated, not assumed)

Recalculating honestly against the earlier ~20-component estimate (which itself assumed the old, secondary-tab-inclusive scope):

- **1 shared component** (`form-next-step-button.component.ts` + `.html`) — new `@Input`s/`@Output` + template branch. Touches every existing consumer only in the sense that the new inputs default to `false`/no-op; no behavior change for any of the 20+ non-primary embed sites.
- **9 primary-step components** (`.ts` + `.html` each) — add the profileCompleteness subscription + `submitDisabled` computation + `onSubmitProfile()` (moved logic) + the three new bindings at each live `<app-form-next-step-button>` embed site (several of the 9 templates embed it 2-3 times, e.g. `startup-information.component.html:1934-1937` live + a second, already-commented-out instance at `:1956-1959` that stays commented; `organization-details.component.html:740-741,759-760,786-787` — 3 live sites all needing the same three new bindings).
- **8 top-bar widget components** (`.ts` + `.html` each) — remove the Submit `<button>` markup, remove `checkAndShowModalForSubmitProfile()`/`onRequestApproval()`/`requestApproval()`/`isSubmitDisabled`(-equivalent) methods and the auto-fire call site, now that the logic lives solely in the primary-step component. The widget component itself is **not** deleted — it still renders percentage text, the missing-fields popover, Edit-Profile button, Share button, and the "under review" badge.

**Total: 18 components (36 physical `.ts`/`.html` files) touched**, versus the earlier draft's ~20-component estimate for the old (secondary-tab-inclusive, flag-dependent-dual-target) scope. This is a **modest reduction** (18 vs. 20 components), not a dramatic one: the shared-component extension eliminates the flag-dependent dual-target problem for Corporate/Mentor/Partner and the two shared-component usage-gating cases (Startup's `pitch-deck-management`, the shared `investments-details`) entirely — those don't need touching at all under decision 1's scope — but the underlying per-type Submit-handler business logic (confirm modal copy, dispatch action, navigation target, threshold) still has to move out of 8 separate widget files and into 9 separate primary-step files regardless of which architecture is chosen, since that logic was never generic to begin with (Finding 2). The shared-component change removes *last-page-detection* duplication, not *per-type business-logic* duplication.

## Critical fix (2026-08-24, found via live testing) — Submit rendered on the wrong (first) page

**The user live-tested Startup's profile form and found Submit rendering on "Basic Information" — the FIRST of 4 tabs — instead of the last.** Root cause: the original implementation hardcoded `[isLastPrimaryStep]="true"` onto whichever single component SAN-497's auto-save work happened to touch per type. For the 6 single-primary-step types (Individual, Corporate, Mentor, Partner, Service Provider, Program Office) that component genuinely is both first and last, so the bug was invisible there. For **Startup** (4 tabs: Basic Information, Industry/Technology, Financials, Pitch Deck) and **Investor org** (3 tabs: Basic Information, Investment Details, Representative Details) and **Investor individual** (2 tabs: Basic Information, Investment Thesis), the component SAN-497 touched is always "Basic Information" — the FIRST tab, not the last. The user's own framing of the fix ("last page pe Submit ana chahiye, agar extra page add ho to uspe ana chahiye") made clear this needed to be genuinely dynamic, not just corrected once for the current tab order.

**Fix:** added `ProfileStepPositionService` (`shared/utils/profile-step-position.service.ts`), which computes "is this URL the last button-capable tab for its type" fresh on every check — the SAME ordered-list logic `IncompleteStepForwardGuard` (SAN-498's fix) already builds: static `PROFILE_NAV_LINKS` entries filtered by feature flag, plus tenant-admin custom-form tabs from the `global` store, minus any entry marked `noStepButton: true` (a page with no Save/Submit slot at all — see below). Every one of the 9 primary-step components now calls `this.isLastPrimaryStep = this.profileStepPositionService.isLastStep(this.router.url)` in `ngOnInit()` instead of hardcoding `true`, and binds `[isLastPrimaryStep]="isLastPrimaryStep"` (not `="true"`) in its template. Because the tab list is rebuilt from live data every time, a future tenant custom-form tab — or a new static tab — automatically becomes the new "last step" with no further code change, closing the same gap class SAN-498's fix closed for tab-navigation blocking.

**`noStepButton` (new field on `PROFILE_NAV_LINKS` entries, `navlinks.ts`):** Startup's "Pitch Deck" tab is a video/document-upload flow with no Save/Submit button slot at all (confirmed by SAN-497's own investigation). Marked `noStepButton: true` so `ProfileStepPositionService` skips it when finding the effective last *button-capable* tab, without affecting `IncompleteStepForwardGuard`'s separate tab-navigation-blocking calculation (which still evaluates Pitch Deck's completeness normally — `noStepButton` only concerns which page renders the physical button).

## Fix (2026-08-26, found via live testing) — clicking Submit never saved the current page's own data first

**Reported live**: "next pe click krne se save ho jani chiye sbhi details" (clicking Next should save all the details) — investigation confirmed "Next Step" already saves-then-navigates correctly everywhere it's wired (`handleNext()` calls the page's own persist method with a navigate-on-success callback). The real gap was on the **Submit** side: `FormNextStepButtonComponent.handleSubmitClick()` (the shared button, rendered instead of Next Step when `isLastPrimaryStep` is true) only ever does `this.submit.emit()` — it has no way to know which save method the embedding page should call first, and every embedding component's own `(submit)` handler (`onSubmitProfile()`) went straight to the Swal submit-confirmation / `SendRequestApproval()` dispatch without ever persisting the current page's field values. So a user who typed something on the true-last page and immediately hit Submit (before the next auto-save tick) could submit for approval with that edit unsaved.

Fixed for all 3 Investor Submit paths (the ones covered by this spec plus the SAN-516 custom-forms wrapper, which the original SAN-500 pass explicitly flagged as unresolved — item 1, "resolve Representative Details' existing button conflict"):
- `organization-details.component.ts` — `onSubmitProfile()` now calls `persistOrganizationInfo(() => this.showSubmitConfirmation(), true)` (silent save, confirmation shown only after it succeeds) instead of going straight to the Swal.
- `individual-investor-edit-form.component.ts` — same pattern; `onSubmit()` gained an `onSuccess` callback param, `onSubmitProfile()` now calls `this.onSubmit(true, () => this.showSubmitConfirmation())`.
- `event-forms.component.ts` (the tenant custom-form renderer embedded by `ExtraInfoInvestorComponent` for both Investor variants' custom-form tabs) — `updateParticipationDetails()` gained an `onSuccess` callback param; the Submit slot's `(submit)` binding changed from `submit.emit()` (immediate, no save) to a new `handleLastStepSubmit()` that saves silently first, then emits `submit` upward to trigger the wrapper's own `onSubmitProfile()`/approval-confirmation flow. (Named `handleLastStepSubmit`, not `handleSubmit`, to avoid colliding with an existing unrelated `handleSubmit()` console.log stub already in this file.)

**Not changed**: the shared `FormNextStepButtonComponent.handleSubmitClick()` itself — it still just emits; the save-then-confirm sequencing lives in each embedding component's own `(submit)` handler, since only that component knows which save method applies. This same architectural gap (Submit not saving first) likely exists for the other 7 stakeholder types' own `onSubmitProfile()`/`onRequestApproval()` handlers too, since they follow the identical SAN-500/SAN-516 pattern — not audited or fixed in this pass, scoped to Investor per the explicit report ("investor wale mein").

**Verification:** `npx tsc -p tsconfig.app.json --noEmit` clean after all changes, including resolving a pre-existing method-name collision this surfaced (`handleSubmit()`) in `event-forms.component.ts`.

## Critical fix (2026-08-26, found via live testing) — `isLastStep()`'s synchronous forms-list snapshot raced against page load

**Reported live**: Service Provider's Basic Information tab (the only tab in its static `PROFILE_NAV_LINKS` array — "Industries" is commented out) rendered a disabled "Submit" button instead of "Next Step", even though a real tenant custom form ("new profile form") sits right after it and should have made it the true last step.

**Root cause**: `ProfileStepPositionService.isLastStep()` read the `global` store's forms list via `this.store.pipe(select(getFormsList)).subscribe(...).unsubscribe()` — a one-shot SYNCHRONOUS snapshot taken at the exact instant it's called. All 16 callers (the 9 primary-step components plus the 7 `Extra*` custom-form wrapper components) invoke it exactly once, in `ngOnInit()`, and assign the boolean result directly to `isLastPrimaryStep` — never recomputed afterward. On a typical fresh page load, `ngOnInit()` runs before the async `getFormsList` HTTP response has actually landed in the store, so this synchronous read saw an **empty** forms array almost every time. For any type whose static array has only one eligible entry (Service Provider today; any type could hit this if a flag/entry situation ever reduces it to one), the combined list collapsed to just that one static tab, so `isLastStep()` incorrectly returned `true` on the *first* page. Because the result was assigned once and never revisited, the mistake was permanent for that page load regardless of how long the custom-forms fetch actually took — unlike a typical loading-spinner race, this one never self-corrected.

**Fix**: added `ProfileStepPositionService.isLastStep$(currentUrl): Observable<boolean>`, a reactive equivalent that maps over the `getFormsList` store selector instead of snapshotting it once — it emits fresh every time the forms list changes, including the very first time it actually loads. All 16 call sites now subscribe (`.pipe(takeUntil(this.destroyed$)).subscribe(res => this.isLastPrimaryStep = res)`) instead of doing a synchronous assignment. The original synchronous `isLastStep()` is left in place (no current callers, but no reason to remove a working, correctly-documented method).

**Verification:** `npx tsc -p tsconfig.app.json --noEmit` clean after the service change and all 16 call-site updates.
