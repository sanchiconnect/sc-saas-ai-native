# Tenant Data Export (Download Backup Data)

## Problem

When a client (tenant) wants to exit the SanchiConnect SaaS product, there is currently no self-serve way for a platform operator to pull a full backup of that tenant's data. This feature adds a "Download Backup Data" entry to the Developer Zone dropdown in `sanchiconnect-saas-tenants-admin` (`adm.tenants.sanchidev.in`) — the platform-operator control panel — so an `is_dev`-role operator can pick a specific tenant, pick which category of that tenant's data to export (single-select, 2026-07-16 — see below), pick an output format (CSV, Excel, or ZIP), and download it.

**Re-scoped 2026-07-15** (was originally scoped to `sc-saas-admin`, per-tenant admin panel — see git history on this file). Corrected because: `sanchiconnect-saas-tenants-admin` already stores every tenant's DB credentials in `tenant_users` (`database_host`, `database_user`, `database_password`, `database_port`, `database_name` — `sanchiconnect-saas-tenants/src/modules/tenants/entities/tenant-users.entity.ts:63-75`), and already has **live, working code that connects to an arbitrary tenant's DB using those columns**: `modules/scrapper.php:7-15` loops every active `tenant_users` row and opens a per-tenant Medoo connection for cross-tenant reporting. This is a better fit than the original plan — a platform operator can action a client's exit request without needing to log into that specific tenant's own `sc-saas-admin` panel.

**Trade-off reversed 2026-07-15 (same day, later):** the generic-dump approach was shipped first, then reviewed against `sc-saas-admin`'s reference export (`modules/csv/export.php`, `table/startups` → CSV) and found insufficient — a raw dump would hand a departing client foreign-key IDs instead of names (e.g. `registered_country: 14` instead of a country name), which isn't a usable backup. Decision: **port the 8 curated per-table cases** already built in `sc-saas-admin/modules/csv/export.php` (`startups`, `mentors`, `investors`, `partners`, `service_providers`, `corporates`, `program_office_members`, `individuals` — joins, ID-to-name resolution) into this repo's handler, adapted to run against the selected tenant's connection. `startups` is added to the **Stakeholders** category bundle (it wasn't in the original bundle definition — an oversight, since it's clearly a stakeholder entity and has its own curated case in the reference file). Generic `getColumns()` dumps remain for the program-data categories — those have no curated reference to port from.

**Simplified 2026-07-15 (product decision, same day):** three simplifications were made to the shipped feature, all in `_data_export_generate.php` / `data_export.php`:
1. **S3 URL resolution removed entirely.** The curated Stakeholders builders no longer resolve file-reference columns (`pitch_document`, `company_logo`, `avatar`, `organization_logo`, `logo`) to public/signed S3 URLs — the `buildTenantS3FileUrl()`/`buildTenantS3SignedUrl()` helpers and the `S3Client` dependency were deleted. Exports now carry the **raw stored value** (an S3 key/path string) in those columns, untouched.
2. **The "Other" category was removed.** A table that matches neither the Stakeholders allowlist nor a program-data prefix pattern is now silently excluded from export — not bucketed into a catch-all.
3. **The "Users" category was removed.** The `users` table (if present) is never categorized/exportable through this tool now — same silent-exclusion treatment as Other.

**Split 2026-07-15 (later still):** "Application/Program data" was split into two separate categories — **Custom Programs Data** (`application_programs` + sub-tables) and **Startup Programs Data** (`programs` + sub-tables, `program_office_members` still excluded — it's a Stakeholder, matched first). A loading overlay was also added while an export generates, for visibility on longer curated exports — originally this app's existing `.contentloader` global loader, **swapped 2026-07-16** for a page-scoped `#loaderOverlay` element (markup/CSS ported from `sc-saas-admin/themes/default/html/elements/footer.php`'s `#loaderOverlay`/`.iframe-modal-overlay`/`.iframe-modal-loader`, per explicit product request) since neither that id nor those CSS classes existed in this repo yet — added inline in `themes/default/html/developer/data_export.php` itself, not to the shared `header.php`/`footer.php`/global stylesheet (page-local, no risk to any other screen).

3 categories exist going forward: **Stakeholders**, **Custom Programs Data**, and **Startup Programs Data**.

**Custom Programs Data curated (2026-07-15, later still):** same reasoning as the Stakeholders reversal — reviewed against `sc-saas-admin`'s reference (`modules/application_management/submission-application-management.php`, the "Download All Applications" action on a Custom Program's detail page) and found the generic dump insufficient here too: applications use a dynamic custom-form-builder schema (`forms`/`forms_submissions`), so a raw dump would show undecoded JSON blobs and numeric field-definition IDs instead of question labels and answers. Decision: port the **"Download All Applications"** variant specifically (of 3 near-identical variants found — "Export All Applications", "Download Submitted Applications", "Download All Applications" — this one covers every status across every round, the most complete "backup" reading) for the **Custom Programs Data** category only (Startup Programs Data was believed at the time to have no equivalent reference — **corrected 2026-07-16, see below**).

**Startup Programs Data curated (2026-07-16):** the "no curated reference exists" assumption above was wrong — found `sc-saas-admin`'s own equivalent, `modules/startup-application-management.php`'s **"Download Program Data"** action (`More Actions` menu on a Startup Program's detail page; same handler is duplicated across `startup-application-management(-tableview).php`, `mentor_application_management.php`, and `venture-studio-application-management.php` — the Startup Programs variant was ported, matching this category's `programs`/`program_startup_rounds` tables). Same insufficiency as Custom Programs Data applies — a raw dump would show ids instead of names and no per-application context — so this category is now curated too. Ported: `getStartupsForProgram()` (`includes/startup_application_management_funcs.php:2325`) for the per-application fields (Application Number/Status/Round, sourced from `program_startup_rounds`), and `startupDataWithCustomForm()`'s per-startup enrichment (founders, advisors, financials, registered location, technologies/industries/business models, product stage) — reused via this repo's own `buildStartupsExportRows()` (already curated for the Stakeholders category's `startups` table, given an optional startup-id filter for this reuse) rather than re-porting the same enrichment logic a second time. Program-specific custom-form fields (`forms` rows whose `programs` JSON column contains the program's id, via `JSON_CONTAINS` + `Medoo::raw()` — this repo's vendored Medoo already special-cases a raw WHERE value containing `JSON_` to emit it as the whole condition, so the reference's exact syntax ports verbatim) resolve through the same `getExportFormDetails()`/`resolveFormAnswers()` helpers already built for Custom Programs Data (the latter renamed from `resolveCustomProgramFormAnswers()` since it's now shared across both categories). Both "submitted" and "pending" `submission_status` values are combined (the reference exposes them as two separate downloads) for the same "most complete backup" reading already applied to Custom Programs Data. No S3 signed URLs — Pitch Deck/Company Logo keep their raw stored value, same rule as everywhere else in this feature. Jury/ratings (`program_rounds_jury`, `startup_ratings` — a separate "Download CSV"/rating-report action in the reference) are **not** included — out of scope, not part of "Download Program Data".

Ported: `getApplicationsForProgram()` (`sc-saas-admin/includes/application_program_management_funcs.php:1263-1344`), `getFormDetails()`/`formatFormSubmissionsData()` (`sc-saas-admin/includes/custom_form_functions.php:540`, `:387`) for dynamic form field label/answer resolution, the draft-submissions append logic, and document-submission/pitch-deck joins (`application_program_document_types`/`application_program_document_submissions`) — all adapted to run against the selected tenant's connection. **No S3 signed URLs** (same rule as Stakeholders, reconfirmed for this category specifically) — document/pitch-deck references keep their raw stored value. Jury/ratings/analysis tables (a separate, adjacent menu item in the reference, `download_ratings_report`) are **not** included — out of scope, not part of "Download All Applications."

**Judgment call, reversed 2026-07-16:** the reference implementation operates on one program at a time (its own detail page). This tool exports a whole tenant, which can have many Custom Programs. The port originally loop every `application_programs` row found in the tenant and combined every program into **one output per format** with a `program_id`/`program_title` column added to identify which program each row belongs to. **Reversed same day** per explicit product feedback: an operator downloading a departing client's Custom Programs Data wants to hand a single program's export to that program's owner without extracting rows out of a combined file first. The category now produces **one file/sheet per program** instead — each still carrying its own `Program ID`/`Program Title` columns (for traceability if a file is later separated from its filename), but no longer merged with any other program's rows. This changes all 3 output formats for this category specifically: **ZIP** bundles one CSV per program (instead of one combined `custom_programs_data.csv`); **Excel** gets one sheet per program (instead of one combined sheet); **CSV** format auto-switches to a zip of per-program files whenever more than one program produces data — the same auto-zip behavior this handler already uses whenever more than one output file is produced (originally also triggered by selecting 2+ categories under CSV format; category selection became single-select later the same day, so that particular trigger no longer applies — the per-program trigger still does). A program that errors or has zero applications is silently omitted — no empty per-program file is produced for it. **Filename convention (2026-07-16):** each per-program file/sheet is named from the **program's own title alone** — no `custom_programs_data` category prefix, no `program_id` suffix — filesystem/zip-entry-sanitized (non-alphanumeric runs replaced with `_`). Two programs sharing an identical title get a numeric suffix (`_2`, `_3`, …) appended to keep filenames unique, same de-duplication approach as the Excel sheet-title collision handling. **Startup Programs Data got the same per-program split applied on top of its own curated port (2026-07-16, explicit product request — "make same download process for startup program data")**: identical per-program file/sheet behavior, identical filename convention (program title alone, de-duplicated), identical auto-zip-on-CSV behavior. Stakeholders' own file layout is unaffected — one file per table (CSV/Excel/ZIP), unchanged.

**Bug fix, 2026-07-16:** the ZIP-format branch previously special-cased Stakeholders into **one combined file per category** (all 8 tables' CSVs concatenated with `## table:` text markers inside a single `.csv`), while the CSV format's own auto-zip path already wrote **one file per table** for Stakeholders (no special-casing) — an inconsistency between the two code paths, not a deliberate design choice. Reported by the operator as "only single stakeholder file downloaded in zip folder" when selecting Stakeholders + ZIP, expecting separate `startups.csv`/`mentors.csv`/etc. files like every other category and output format already produces. Fixed by making the ZIP branch match the CSV branch exactly: one file per unit (one per table for Stakeholders, one per program for Custom/Startup Programs Data) inside the category's subfolder, no combined-file special case left anywhere in the handler.

**Security note:** `modules/scrapper.php` (the connection precedent) has **no role gate at all** — only `checkLoggedIn()`. This is not the pattern to copy for permissions. This feature reuses the same `checkRole("is_dev")` gate already used by this repo's own `modules/developer/database_management.php:5`, `api_management.php:4`, `form_fields_management.php:5`. Audit logging was considered (this repo has no existing audit-log mechanism, unlike `sc-saas-admin`'s `createAdminLogs()`/`spa_admin_logs`) but is explicitly **out of scope** per product decision (2026-07-15) — not being added.

## Acceptance criteria

- [ ] An `is_dev`-role operator sees a new "Download Backup Data" entry in the Developer Zone dropdown, added to the array returned by `getDeveloperMenus()` (`includes/core_functions.php:98`), following the existing `{title, link, icon, target}` shape.
- [ ] Loading the new page/action directly by URL as a non-`is_dev` session redirects away, matching the pattern in `modules/developer/database_management.php:5-8`.
- [ ] The screen lets the operator pick one active tenant (from `tenant_users` where `active = "1"`, the same filter `modules/scrapper.php:7` already uses) via a searchable selector — plain `<select>` is fine if the theme doesn't already have a search-enabled dropdown component; check the theme's existing JS libs before adding a new one.
- [ ] Selecting a tenant opens a per-tenant Medoo connection using that row's `database_host`/`database_name`/`database_user`/`database_password`/`database_port`, exactly matching `modules/scrapper.php:9-16`'s connection shape — never the platform `$database` connection, and never accepting a DB host/name/credentials from anything other than the looked-up `tenant_users` row itself (no client-supplied connection parameters).
- [ ] Tables from that tenant's DB are enumerated dynamically (`SHOW TABLES FROM` + `getColumns()`, adapting `modules/developer/database_management.php:103-150` to run against the selected tenant's connection instead of the platform DB) and grouped into exactly **3 categories**: **Stakeholders** (`startups`, `investors`, `mentors`, `corporates`, `service_providers`, `partners`, `individuals`, `program_office_members`), **Custom Programs Data** (`application_programs` + its rounds/jury/submissions/ratings/analysis sub-tables), and **Startup Programs Data** (`programs` + its rounds/jury/faqs/submissions sub-tables) — one radio option per bundle, not per table (**changed from checkboxes to a single-select radio group, 2026-07-16 — see below**). Any table matching no bucket (including `users`) is silently excluded from export — **Users and Other categories were removed by explicit product decision (2026-07-15)** and no longer exist.
- [ ] **Single-category selection (2026-07-16 product decision, reversing the original multi-select design):** the operator selects exactly **one** category (radio buttons, first option pre-checked — same pattern as Output format, which was already single-select) and exactly one output format (CSV, Excel, or ZIP) before generating. Reversed after selecting all 3 categories together produced a server error — combining Stakeholders' 8 curated queries with Custom Programs Data's and Startup Programs Data's per-program loops (each itself issuing several queries per program) in a single request was too heavy/fragile to keep supporting; the underlying resource limits were not root-caused, this is a scope reduction, not a fix to a diagnosed bug. The backend (`_data_export_generate.php`) reads a single `category` POST field (was `categories[]`) into a one-element `$selectedCategoryKeys` array, so the rest of the category-loop pipeline (unit-building, CSV/Excel/ZIP branches, per-category zip subfolders) — already written generically over an array — is unchanged.
- [ ] **Stakeholders category**: each of the 8 tables (`startups`, `mentors`, `investors`, `partners`, `service_providers`, `corporates`, `program_office_members`, `individuals`) uses the curated query/joins/ID-resolution ported from `sc-saas-admin/modules/csv/export.php`'s matching `case` block, adapted to run against the selected tenant's connection — not a generic dump. **No S3 URL resolution is performed** (removed by explicit product decision, 2026-07-15): file-reference columns (`pitch_document`, `avatar`, `organization_logo`, `logo`) are exported with their raw stored value (an S3 key/path string) exactly as read from the base query. `company_logo` (`startups`, `corporates`) is dropped from the export entirely, not just left unresolved — removed by explicit product decision, 2026-07-16 ("remove company logo url no need of this").
- [ ] **Custom Programs Data category**: curated "Download All Applications" export ported from `sc-saas-admin/modules/application_management/submission-application-management.php`, adapted to run against the selected tenant's connection and loop across every `application_programs` row in that tenant (not a single program). **Split per program (2026-07-16)**: each program produces its own file/sheet — not combined into one dataset — still carrying its own `Program ID`/`Program Title` columns. A program with zero applications, or whose query fails, is silently omitted (no empty file for it). Dynamic custom-form field labels/answers are resolved (not raw JSON). No S3 signed URLs — document/pitch-deck references keep their raw stored value.
- [ ] **Startup Programs Data category**: curated "Download Program Data" export ported from `sc-saas-admin/modules/startup-application-management.php`, adapted to run against the selected tenant's connection and loop across every `programs` row in that tenant (not a single program). **Split per program (2026-07-16)**, same as Custom Programs Data: each program produces its own file/sheet, named from the program's own title alone. Combines both "submitted" and "pending" applications. Per-startup profile fields (founders, advisors, financials, location, technologies) are resolved via this feature's own curated `startups` builder (reused, not re-ported), and program-specific custom-form field labels/answers are resolved (not raw JSON). A program with no applications is silently omitted (no empty file for it). No S3 signed URLs — document/pitch-deck/logo references keep their raw stored value.
- [ ] A full-page loading overlay (`#loaderOverlay`, page-scoped markup/CSS ported from `sc-saas-admin`'s `#loaderOverlay`/`.iframe-modal-overlay`/`.iframe-modal-loader`, 2026-07-16 — not this app's `.contentloader`) shows while an export generates, alongside the button's spinner state.
- [ ] Excel output: via `phpoffice/phpspreadsheet` (new composer dependency, matching `sc-saas-admin`'s `^5.7` — confirm compatibility with this repo's actual PHP runtime, not just its stale `"php": ">=5.5.0"` composer floor). **One `.xlsx` FILE per unit** — one file per table for Stakeholders, one file per program for Custom Programs Data and Startup Programs Data — bundled with the existing `Zipper` class whenever more than one file results, exactly mirroring CSV/ZIP's own "one file per unit" rule; a single-unit export still downloads directly as one `.xlsx`, no zip wrapper. **Bug fix, 2026-07-16:** this branch previously always produced ONE combined `.xlsx` workbook with one SHEET per unit (e.g. all 8 Stakeholders tables as 8 sheets in a single file) regardless of unit count — reported by the operator: "you downloaded the data in excel format, but added all the stakeholders in sheets in a single file. i want separate files for all stakeholders, application_programs, programs." Fixed to build one spreadsheet file per unit instead of one sheet per unit, same day as (and for the same underlying reason as) the ZIP-format single-combined-file bug fix above.
- [ ] ZIP output: bundles one file **per unit** using this repo's existing `Zipper` class (`core/filemanager.php:206`, confirmed present and identical in shape to `sc-saas-admin`'s) — one file per table for Stakeholders, one file per program for Custom Programs Data and Startup Programs Data (2026-07-16 bug fix: previously Stakeholders was wrongly combined into a single file per category in this branch only, inconsistent with the CSV format's own auto-zip path).
- [ ] CSV output: one flat file when exactly one file's worth of data results; auto-zips (same `Zipper` class) whenever more than one file results — including when Custom Programs Data or Startup Programs Data alone expands to more than one program.
- [ ] **Per-category subfolders in every multi-file zip (2026-07-16, explicit product request):** whenever a zip is produced (either output format is ZIP, or CSV format auto-zips because more than one file resulted), every file is written under a subfolder named for its category — `Stakeholders/`, `Custom Programs Data/`, `Startup Programs Data/` (filesystem/zip-entry-sanitized the same way per-program filenames are) — never flat at the zip root. `Zipper::addFileOrDir()`'s single-argument `ZipArchive::addFile()` call preserves whatever relative path it's given as the in-zip entry name, so writing `"<CategoryFolder>/<file>.csv"` into the scratch dir before zipping is sufficient — no change needed to the `Zipper` class itself. `cleanupExportScratchDir()` was made recursive to match (it previously only unlinked top-level files, which would have silently failed to remove — and leaked — these new per-category subfolders).
- [ ] No audit logging is added (product decision, 2026-07-15) — do not build a new logs table or call any logging function for this action.
- [ ] Generation is synchronous — the handler streams the response directly, no persisted file, no queue.

## Contracts & invariants

- **Flags:** None added. Gated by the existing `is_dev` session role (`checkRole("is_dev")`), same mechanism already used by this repo's `database_management.php`, `api_management.php`, `form_fields_management.php`.
- **API:** None. No `sc-saas-backend` change — this reads the target tenant's DB directly via Medoo, the same way `modules/scrapper.php` already does.
- **Events:** None.
- **Invariants at risk:** This repo has **no tenant-scoping mechanism by design** (per its own `CLAUDE.md` — it's a platform-operator tool operating on global cockpit data) — this feature is the **second** deliberate, ad-hoc exception to that (after `modules/scrapper.php`), not a violation of a rule that applies here. The safety property that matters instead: the per-tenant connection must be opened **only** from a server-side lookup of the operator's explicit tenant selection against the real `tenant_users` row (id + `active = "1"`), never from a client-suppliable host/credential value. Call this out explicitly in code review — it's the one place this feature could go wrong.

## Test plan

- `sanchiconnect-saas-tenants-admin` has no automated test framework (`php -l` only). Run `php -l` on every new/edited file. Manually verify: (a) an `is_dev` session sees and can open the new menu entry; (b) a non-`is_dev` session hitting the URL directly is redirected; (c) the tenant selector only lists `active = "1"` tenants; (d) CSV/Excel/ZIP each open correctly for at least one real tenant in a local/staging setup; (e) selecting a different tenant produces that tenant's data, not a previously-selected one (no session/connection bleed between requests).
- cross-repo: none required.

## Rollout

Single-repo, no flag, no migration. The Developer Zone menu entry itself is the rollout gate (`is_dev`-only, already a small trusted population).

## Out of scope

- Any change to `sc-saas-admin`, `sc-saas-backend`, `sc-saas-frontend`, or `sanchiconnect-saas-tenants`.
- Jury/ratings data for either program category (`program_rounds_jury`, `startup_ratings`, and Custom Programs Data's equivalent analysis tables) — a separate, adjacent action in both reference implementations (`download_ratings_report` / rating-report CSVs), not part of either "Download All Applications"/"Download Program Data" flow this feature ports. All 3 categories are now curated — no generic-dump category remains.
- Audit logging of export actions — explicit product decision (2026-07-15), not being added.
- The **Users** and **Other** categories — removed entirely by explicit product decision (2026-07-15); a table matching neither remaining bucket is silently excluded from export, not bucketed into a catch-all.
- S3 URL resolution for stakeholder file-reference columns — removed entirely by explicit product decision (2026-07-15); exports carry the raw stored S3 key/path string.
- Automated/scheduled/recurring backups.
- Data import or restore tooling (export-only).
- A new feature flag — reuses the existing `is_dev` role gate.
- Bulk multi-tenant export in a single action — one tenant selected per export, per the tenant-scoping safety property above.
- Background/async export generation — synchronous streaming only.
